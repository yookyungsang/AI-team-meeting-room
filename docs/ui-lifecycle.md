# 화면 높이와 닫힘 처리 · 0.3.1

## 확인한 결함

기존 화면은 대화 영역의 높이를 `100dvh - 260px`로 계산했습니다. 내용 크기에 맞춰 iframe 높이를 바꾸는 호스트에서 이 높이를 다시 측정하면, 나머지 헤더·입력창·접힌 제어 영역의 실제 높이와 260px의 차이가 매번 누적됩니다. 전체 화면에서 inline으로 돌아올 때도 별도 처리가 없었습니다.

독립 Chromium 호스트 모형에서 이전 소스는 20번 재측정하는 동안 높이가 1,107px에서 3,140px로 매번 107px씩 증가했습니다. 이는 사용자가 보고한 흔들림의 가능한 원인을 실제 레이아웃으로 재현한 결과입니다. Codex 자체의 오버레이/스크롤 동작 전체를 재현했다는 뜻은 아닙니다.

또한 `ui/resource-teardown` 응답과 종료 정리가 없어 호스트의 닫힘 요청을 처리하지 못했습니다. 단순한 document visibility만으로는 종료 상태를 보장할 수 없었습니다.

## 수정

- Inline 기본 높이는 iframe viewport와 독립적인 720px이며 호스트의 명시적 높이 제한을 적용합니다. 전체 화면은 호스트의 고정 높이를 사용합니다.
- 헤더·대화·입력·하단 제어는 하나의 제한된 flex 영역 안에 배치합니다. 내용이 길면 내부에서 스크롤합니다.
- 호스트 context 변경을 병합하며 화면 모드만 바뀌면 이전 모드의 크기를 재사용하지 않습니다.
- Flexible 높이 알림은 실제 목표 높이가 바뀔 때만 보냅니다.
- 닫힘 요청에는 응답하고 타이머·대기 중 RPC를 정리합니다. pagehide도 같은 정리를 수행합니다. 늦게 도착한 상태와 이벤트는 종료된 화면을 되살리거나 새 작업을 보내지 못합니다.
- 호스트 요청 ID와 화면 요청 ID는 별개이므로, 종료 요청을 대기 중 응답 ID보다 먼저 구분합니다.

## 검증

2026-10-28 기준 32개 Node 검사가 통과했습니다. 여기에는 전체 화면/inline 전환, 종료 시 ID 충돌, 진행 중 조회 종료, 늦은 이벤트, pagehide 검사가 포함됩니다.

실제 Chromium 엔진의 격리된 호스트 모형에서 너비 1,280px와 420px 각각 20회 모드 전환 및 20회 높이 재측정을 수행했습니다. 수정본은 매번 720px로 유지됐고 입력창과 대화 영역이 겹치지 않았습니다. 종료 응답 후 4.2초 동안 추가 상태 조회나 모델 메시지가 없었습니다. 테스트 자료는 `.local/`에만 저장됩니다.

Codex 앱에서 사용자가 겪은 빠른 상하 움직임이 완전히 사라졌는지는 새 플러그인을 로드한 뒤 실제 닫기/축소 동작으로 확인해야 합니다. 이 문서의 브라우저 검사를 실제 Codex 검증으로 표시하지 않습니다.

## 프로토콜 근거

[공식 MCP Apps 규격](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)의 Container Dimensions, Host Context 변경 및 Resource Teardown 절차를 따릅니다. 호스트가 고정 높이를 주는 경우와 화면이 높이를 결정하는 경우를 구분하고, 닫기 전에 리소스를 정리하도록 정의되어 있습니다.

## 0.3.2 · 하단 공간 확보

팀과 회의 제어, 요청 처리 기록, 전송 안내를 상단 메뉴 버튼의 modal dialog로 옮겼습니다. 평상시 하단에는 입력창만 남으며 메뉴를 열어도 대화 영역의 높이나 입력창 위치는 바뀌지 않습니다. 닫기 버튼·Escape·바깥쪽 클릭으로 닫을 수 있고 키보드 포커스는 메뉴 버튼으로 돌아갑니다. 기존 프로젝트 연결과 전송/조회 정책은 그대로 유지합니다.

## 0.3.3 · Enter 전송 중심 입력창

큰 전송 버튼을 화면과 탭 순서에서 제거했습니다. 내부 submit 요소와 기존 전송 가능 여부 검사는 유지하여 Enter 전송, Shift+Enter 줄바꿈, 한국어 IME, 빈 입력·일시정지·중복·실패 후 불확실 상태의 보호 동작을 보존합니다. 입력창에는 작은 키보드 안내를 연결했습니다. 상단 회의실 메뉴와 프로젝트 연결·실제 대화 데이터는 변경하지 않습니다. 실제 Codex 화면 검증은 별도이며 독립 브라우저 결과와 구분합니다.

## 0.3.7 · 작업 중 추가 메시지

기존에는 저장부터 `ui/message` 응답까지 하나의 전송 잠금을 유지했고, 15초 응답 지연이나 실패가 회의실 전체의 새 전송을 막았습니다. 이제 저장 중에만 짧게 잠그며, 각 메시지의 전송 확인 대기·확인 필요·거절·호스트 전달 확인을 별도로 표시합니다. 지연된 응답은 계속 수신하되 새 초안이나 다른 프로젝트의 입력을 지우지 않습니다. 확인 대기·불확실 상태의 동일 본문은 중복 전송하지 않으며, 다른 추가 내용은 계속 보낼 수 있습니다. 자동 재전송은 추가하지 않습니다.

추가 메시지는 별도 요청 ID와 `followUpTo`로 가장 최근의 활성 원래 요청에 연결됩니다. `room_get`은 연결된 추가 요청을 반환하고, 총괄은 중간 판단 및 완료 전에 확인해 현재 작업에 반영합니다. 원래 담당자의 전달 예약을 초기화하거나 이미 진행 중인 작업을 새로 시작하지 않습니다. 미처리 추가 요청은 총괄의 원래 최종 답변 저장만 막습니다. 추가 메시지의 전달이나 구현·수정 작업은 막지 않습니다. 실패한 추가 요청도 성공한 것으로 무시할 수 없습니다. 이미 완료된 원래 요청에는 새 연결을 저장하지 않고, 초안을 유지한 채 새 요청으로 보내도록 안내합니다.

[OpenAI MCP Extensions 규격](https://github.com/openai/mcp-extensions/blob/main/docs/spec.md#uimessage-extensions)의 `target: active, send: true`로 각 사용자 전송을 한 번 전달합니다. 이 규격은 실행 중인 턴을 강제로 중단하는 필드를 정의하지 않습니다. [호스트의 후속 메시지 설정](https://learn.chatgpt.com/docs/app/settings)에 따라 활성 작업 조정 또는 다음 턴 대기가 적용될 수 있으며, 긴 도구 실행 도중 즉시 수정 반영을 보장하지 않습니다. 별도 모델 실행 환경이나 유휴 AI 호출은 추가하지 않았습니다.

40개 Node 검사에서 진행 중 추가 요청 연결, 완료 누락 방지, 프로젝트 격리, 중복 방지, 지연·역순 응답, 닫힘 후 늦은 전달 차단을 확인했습니다. 너비 1,280px와 420px의 독립 Chromium 모형에서는 첫 전송 응답을 보류한 상태에서 두 번째 전송과 초안 보존, 기존 높이·키보드·종료 처리가 통과했습니다. 실제 Codex의 실행 중 메시지 도착 시점과 native 화면 전환은 미검증입니다.
