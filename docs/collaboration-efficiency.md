# 협업 효율 운영 규칙

0.4.0부터 [작업 제어 도구](../host-plugin/skills/team-room/references/work-controls.md)가 관리 대상 파일 편집·검증의 소유권과 재시도 한도를 검사하고, 체크포인트 복구와 로컬 사용량 기록을 지원합니다. 허용된 작업 폴더를 먼저 설정하며 기존 운영 규칙과 승인 범위는 유지합니다. 완료 후 담당자별 측정치만 표시하고 정기 AI 보고를 추가하지 않습니다. 외부 편집기·직접 명령을 전역 차단하거나 미확인 사용량을 0으로 추정하지 않습니다.

2026-10-28 사용자 승인으로 적용합니다. 이 규칙은 업무 처리 기준이며, 새로운 채팅 연결·외부 메시지·비용·배포 권한을 부여하지 않습니다.

2026-10-29 사용자 요청으로 [모든 프로젝트의 협업 지침 전문](../host-plugin/skills/team-room/references/collaboration-policy.md)을 플러그인에 포함했습니다. 총괄 12개 항목, 프로그래머 병렬 협업 9개 절, QA 오류 대응 8개 규칙 및 역할·인계·소통·스킬·모델 선택 기준을 함께 적용합니다. 특정 프로젝트의 원본 폴더나 담당자 명단에 의존하지 않으며 각 프로젝트의 사용자 지정과 승인·도구 제한을 우선합니다. 이 문서는 효율 운영의 요약이고 세부 기준은 패키지에 포함된 전문을 따릅니다.

2026-10-30 요청으로 [새 팀 구성·모델 선택](../host-plugin/skills/team-room/references/team-creation.md)을 지원합니다. 새 대화창 생성에 대한 명시적 사용자 요청이 있을 때만 총괄·기획자·디자이너·프로그래머 2명·QA 구성을 준비하고, 실제 호스트 도구와 사용자의 모델 선택으로 연결합니다. 기존 담당자를 대체하거나 일반 업무 중 부족한 담당자를 임의로 만들지 않습니다. 초기 설정 턴에는 정상 사용량이 있고 정기 AI 호출·설정 확인 왕복은 추가하지 않습니다.

## 역할과 의견 교환

총괄은 원래 배정 턴에서 [UI 배정 기준](../host-plugin/skills/team-room/references/collaboration-policy.md#ui-디자인-판단과-단순-수정의-배정-기준)을 확인합니다. 배치·조작·가독성 판단이 남으면 기존 디자이너가 필요한 짧은 사양만 검토하고, 기존 승인 디자인을 그대로 따르는 단순 수정은 개발자가 바로 처리합니다. 독립 로직은 병행하고 판단이 필요한 UI만 인계에 의존하게 합니다. 전원 회의·매번 새 시안·별도 분류 AI·규칙 확인용 호출은 추가하지 않습니다.

개발 인원은 이번 업무에 실제 배정한 기존 프로그래머 수를 기준으로 합니다. 1명이면 순차 구현·자체 점검 후 QA 인계, 여러 명이면 필요한 기능·파일·의존성 분담과 통합을 적용합니다. 등록 인원이 많아도 작은 작업에는 한 명만 배정하며, 인원을 채우는 호출·가상 동료·의무 단체 검토를 만들지 않습니다. 독립 QA와 단일 파일/Editor 소유권은 인원수와 무관하게 유지합니다. [인원별 적용 기준](../host-plugin/skills/team-room/references/collaboration-policy.md#프로그래머-병렬-협업-전문)을 따릅니다.

시각 디자인은 [디자이너 전용 협업 규칙](../host-plugin/skills/team-room/references/design-collaboration.md)을 실제 배정 때 관련 부분만 확인합니다. 기존 규격을 재사용하고 필수 누락만 묶어 질문하며, 대표 시안·수정 묶음·개발자 인계와 실제 적용·QA 상태를 구분합니다. 다음 인계에는 변경분만 보내고 규칙 공지·반복 검토용 AI 호출을 추가하지 않습니다.

효과음 업무는 [효과음 협업·최종 음원 첨부](../host-plugin/skills/team-room/references/sound-collaboration.md)를 적용합니다. 제작·게임 연결·독립 QA를 구분하고 최종 음원은 제작자가 직접 첨부합니다. UI 미리듣기는 사용자 선택 시에만 파일을 가져와 재생하며 원본 바이트를 모델 문맥으로 전달하거나 AI를 호출하지 않습니다. 실제 청취와 게임 검증의 미완료 상태를 보존합니다.

총괄은 같은 최초 배정에서 [음향 배정 기준](../host-plugin/skills/team-room/references/collaboration-policy.md#음향-판단과-단순-연결오류-수정의-배정-기준)을 적용합니다. 음원 선정·제작이나 재생·음량·겹침 판단이 필요하면 기존 효과음/음향 담당자가 짧게 참여합니다. 정해진 음원 연결·명확한 오류는 개발자가 바로 처리하고 소리 영향 없는 작업은 호출을 생략합니다. 기존 음원·명세를 우선 활용하며 독립 작업은 병행합니다. 별도 분류 AI·정기 호출·의무 제작은 없고 실제 검토·제작에는 일반 사용량이 있습니다.

총괄은 전체 설계, 사용자 범위 안의 기획 승인, 우선순위, 작업 배분, 충돌 조율, 검증 검토와 결과 통합을 맡습니다. 구현·디자인·QA는 필요한 기존 담당자에게 배분합니다. 운영 규칙과 문서는 총괄이 관리합니다. 파일당 한 명만 편집합니다.

일반 작업의 쟁점은 의미 있는 질문·답변 1~2회로 마무리합니다. 지시가 충분하면 회의를 생략합니다. 횟수를 채우기 위한 회의, 수신 확인·감사·게시 확인의 왕복은 하지 않습니다. 의견 충돌, 검증 실패, 필수 정보 부족, 새 장애가 있을 때만 이유와 남은 결정을 짧게 적고 추가 협의합니다. 횟수 제한을 지키기 위해 미해결 문제를 숨기거나 완료 처리하지 않습니다.

## 지속 적용할 역할과 검증 인계

선택한 역할 종류의 [공통·전문 지침](../host-plugin/skills/team-room/references/role-guidance.md)은 실제 첫 배정의 짧은 참조로 전달합니다. 공통은 세션에서 한 번, 전문은 필요한 절만 읽습니다. 직접 입력은 공통과 실제 배정 조건만 적용하고 기존 배정의 역할을 새 표시 명칭으로 바꾸지 않습니다. 저장 공지·역할 확인용 AI 호출은 추가하지 않습니다.

사용자가 프로젝트별로 지정한 역할을 우선합니다. 아래는 해당 역할의 담당자가 연결된 팀에서 사용하는 기본 책임이며, 없는 역할을 임의로 생성하거나 다른 프로젝트에 특정 사람을 배정하지 않습니다.

| 역할 | 책임 | 주요 산출물 |
| --- | --- | --- |
| 총괄 디렉터 | 전체 설계, 기획 승인, 우선순위, 작업 배분, 충돌 조율, 결과 통합과 최종 승인 | 승인 범위, 담당·파일 소유권, 최종 판단 |
| 기획자 | 게임 시스템, 밸런스, 레벨 디자인 | 시스템 규칙, 수치와 근거, 진행·난이도·레벨 설계, 완료 기준 |
| 디자이너 | 캐릭터, UI, 배경, 3D 에셋 기획 | 시안, 스타일·배치·에셋 사양, 기존 자산 활용 계획 |
| 프로그래머 | 구현, 버그 수정, 컴파일·정적 검사와 가벼운 개발자 자체 점검 | 변경 코드, 자체 점검 결과, QA 실행 방법과 알려진 한계 |
| QA | 테스트 케이스 설계, 오류 재현, 실제 화면·동작 및 회귀 검증 | 재현 절차·기대/실제 결과·증거, 통과·실패·미검증 판정 |
| 효과음 담당자 | 효과음 방향, 음원 사양·선정, 재생 조건 검토 | 음원 후보·출처·길이·반복·음량·재생 조건 |

프로그래머의 자체 점검을 QA 검증으로 대체하지 않습니다. 구현과 가벼운 점검을 마치면 변경 파일, 재현 방법, 자체 점검 결과와 한계를 QA에게 인계합니다. QA는 영향 범위의 테스트 케이스를 선정하고 실제 검증을 한 번의 관련 배치로 수행합니다. 결함은 근거와 함께 구현 담당자에게 전달하고, 수정 뒤 실패·새 영향 사례만 재검증합니다. 총괄은 결과를 검토해 승인·통합합니다.

공유 앱이나 Unity Editor는 한 번에 한 명만 조작합니다. 구현 담당자가 사용을 마치면 QA에게 조작권을 명시적으로 인계하고 검증 중 대상 파일을 동시에 수정하지 않습니다. 담당 변경만을 이유로 이미 통과한 검사를 반복하지 않습니다. QA가 연결되지 않았거나 실행 권한·환경이 없으면 총괄이 대체 담당과 한계를 명시하며, 개발자 자체 점검만으로 독립 QA 완료를 주장하지 않습니다.

역할은 대화 기억에만 의존하지 않습니다. 프로젝트 AGENTS.md와 협업 문서에 실제 담당·책임을 저장하고, 담당자는 작업 시작 시 해당 지침을 확인합니다. 총괄은 다음 필요한 배정마다 역할·수정 소유권·검증 책임을 포함합니다. 변경 공지나 기억 확인만을 위해 전원을 호출하거나 주기적으로 재알림하지 않습니다. 다른 사용자의 명시적 역할 변경은 이 기본값보다 우선합니다.

## 압축 전달 형식

게시 전에 [사용자 언어 유지 규칙](../host-plugin/skills/team-room/references/report-language.md)을 같은 보고 작성 턴에서 한 번 점검합니다. 명시적으로 지정한 출력 언어, 해당 프로젝트·원래 요청에서 사용자가 계속 쓰던 언어를 따르고 인용·코드·로그 때문에 바꾸지 않습니다. 총괄은 다음 필요한 배정·인계에만 짧은 보고 언어를 전달합니다. 원문 근거와 사용자 입력은 유지하며 별도 번역·언어 판정 AI나 점검 턴·정기 호출·재게시를 만들지 않습니다.

사용자에게 보이는 보고는 처음부터 개발 지식 없이 이해할 수 있는 자연스러운 존댓말로 씁니다. `text`에 완성한 것·남은 문제·다음 할 일을 먼저 설명하고, 같은 게시물의 `details`에 정확한 파일명·설정·검사 기록·기술 근거를 보관합니다. 상세는 화면에서만 접어 두며 담당자 조회에는 전문이 그대로 제공됩니다. 실패·미검증·승인 필요·권한 및 보존 조건은 쉬운 본문에도 남깁니다. "approval 보존" 대신 "이미 승인받은 내용은 그대로 유지했어요"처럼 뜻을 설명합니다.

담당자끼리도 "이 부분은 두 줄로 나눠도 될까요?"에 "네. 두 줄로 나누고 버튼 크기는 유지해 주세요"처럼 실제 문제를 자연스럽게 묻고 답합니다. 필요한 정확한 테스트명·코드 위치·로그·재현·계약은 상세와 실제 인계에 유지합니다. 질문을 억지로 만들거나 인사·수신 확인·감사만 반복하지 않습니다. 전달·배정·검증 절차를 바꾸거나 별도 AI 재작성·중복 총괄 게시를 추가하지 않습니다. 검증 중 앞선 단계에서 막혔다면 목표 기능을 검증하지 못했음을 구분해 보고합니다.

필요한 최초 요청·승인 범위·제약과 함께 다음만 전달하고, 후속 전달에는 이전 내용의 변경분만 씁니다.

- 결정 사항
- 미해결 문제와 필요한 판단
- 변경 파일과 편집 담당자
- 관련 검증 결과, 실패·미검증 항목, 증거 위치

전체 대화·전체 로그·프로젝트를 매번 복사하지 않습니다. 원문은 필요한 부분만 조회합니다. 승인 제한과 실패 사실은 압축 과정에서 빠뜨리지 않습니다. 담당자 자신의 의미 있는 질문·답변을 회의실에 직접 남기는 방식은 유지합니다.

## 이벤트 기반 진행

배정 후 [완료·문제 중심 대기 기준](../host-plugin/skills/team-room/references/event-waiting.md)을 적용합니다. 총괄은 실제 진행 중인 대상을 한 native wait_threads에 묶고 최신 cursor를 이어가며, 끝난 대상은 제외합니다. 호스트와 현재 대화의 응답성/실행 제한이 허용하면 지원되는 기본 이벤트 대기를 사용합니다. 짧은 고정 간격이나 60초 상한을 모든 환경에 강제하지 않고 더 짧은 실제 제한은 우선합니다. 시간초과에 변화가 없으면 추가 상태/이력/명단 조회·진행 질문·요약 없이 cursor만 이어가거나 독립 업무를 합니다. 완료·실패·막힌 판단·새 사용자 지시에 필요한 내용만 확인합니다.

담당자의 최종 턴을 완료 이벤트로 받으면 별도 완료 통보 메시지를 또 보내지 않습니다. 일상 진행은 회의실에만 기록하고 총괄에게 native 진행 알림을 중복 전달하지 않습니다. 작업을 막는 실제 판단 요청은 검증된 사용자 연락 승인 안에서 필요한 대상에게 한 번 전달합니다. 주기적 AI heartbeat/cron은 만들지 않습니다. 일반 UI의 로컬 기록 갱신은 유지하되 AI를 호출하지 않습니다.

이미 종료된 총괄 턴을 완료·예상치 못한 담당자 중단 시 재개하는 기능과 사용자 권한이 실제 확인된 경우에만 대기를 넘깁니다. 담당자의 직접 완료 메시지만으로는 담당자 자신의 중단을 발견할 수 없습니다. 현재 로컬 연동에서 그 보장이 없으면 활성 이벤트 대기를 유지하고 자동 재실행을 구현했다고 주장하지 않습니다. 불확실한 native 전달을 자동 재시도하지 않고 반복 조회 오류는 한계를 보고합니다. 대기·지침에는 일반 문맥 사용량이 남으며 특정 절감률은 측정 전 단정하지 않습니다.

## 변경 중심 검수와 로컬 도구

[반복 조회와 막힌 질문 알림](../host-plugin/skills/team-room/references/read-notices.md)은 같은 담당자·요청·옵션의 변화 없는 30초 내 room_get 반복을 짧은 정상 응답으로 줄입니다. 다른 담당자의 첫 조회·새 내용·필요한 판단/복구/근거/사용자 재조회는 유지합니다. UI와 native 조회는 차단하지 않습니다. 실제 막힌 question/blocker의 notifyDirector:true는 원문을 보존하고 첫 저장에만 짧은 총괄 알림 전달을 허용합니다. 같은 총괄 대상 peer 전송·저장 재시도로 중복 알림을 만들지 않으며 실제 native 전달과 사용자 연락 승인은 별도로 확인합니다.

총괄의 QA 재검증 지시는 기존 배정 턴에서 [재개 승인과 지시를 한 번에 기록](../host-plugin/skills/team-room/references/work-controls.md#retest-directives-and-execution-keys)합니다. 여러 사례를 묶어 저장하고, 반환된 새 실행 키로 필요한 범위만 검사합니다. 같은 호출의 저장 재시도만 원래 키·내용을 유지하며, 별도 승인 확인·키 복구 왕복·중복 게시·AI 감시를 추가하지 않습니다.

변경 diff, 직접 연결된 호출부·데이터 계약·관련 테스트·필수 프로젝트 지침부터 확인합니다. 공통 인터페이스 변경, 의존성 위험, 실제 실패나 설명되지 않는 동작이 있을 때만 이유를 밝히고 범위를 넓힙니다. 구현 후 관련 검증을 한 번 모아 실행하고 실패·후속 수정 영향 사례만 재검사합니다. 문서만 바뀐 경우 앱이나 Unity를 실행하지 않습니다.

파일 변경 확인은 git diff --name-only, 형식 확인은 git diff --check, JavaScript 문법 확인은 node --check를 사용합니다. 변경 관련 node --test 파일을 선택하며 저장소/브리지 변경에는 기존 npm test 규칙을 따릅니다. 레이아웃 변경은 scripts/check-layout.mjs로 확인합니다. 로그는 로컬에 두고 범위·결과·실패·증거 경로만 전달합니다. 같은 결과가 반복됐다는 이유로 AI나 회의를 호출하지 않습니다. 해석, 충돌, 예상 밖 실패, 승인 판단이 필요할 때 AI가 개입합니다.

규칙 적용을 위한 별도 상주 감시 프로그램은 만들지 않습니다. 실제 절감률은 측정 전에는 단정하지 않습니다. 적용 안내만을 위해 모든 담당자를 깨우지 않고 다음 필요한 업무 배정에 규칙을 포함합니다.
