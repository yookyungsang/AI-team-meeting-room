# 협업 효율 운영 규칙

2026-10-28 사용자 승인으로 적용합니다. 이 규칙은 업무 처리 기준이며, 새로운 채팅 연결·외부 메시지·비용·배포 권한을 부여하지 않습니다.

## 역할과 의견 교환

총괄은 전체 설계, 사용자 범위 안의 기획 승인, 우선순위, 작업 배분, 충돌 조율, 검증 검토와 결과 통합을 맡습니다. 구현·디자인·QA는 필요한 기존 담당자에게 배분합니다. 운영 규칙과 문서는 총괄이 관리합니다. 파일당 한 명만 편집합니다.

일반 작업의 쟁점은 의미 있는 질문·답변 1~2회로 마무리합니다. 지시가 충분하면 회의를 생략합니다. 횟수를 채우기 위한 회의, 수신 확인·감사·게시 확인의 왕복은 하지 않습니다. 의견 충돌, 검증 실패, 필수 정보 부족, 새 장애가 있을 때만 이유와 남은 결정을 짧게 적고 추가 협의합니다. 횟수 제한을 지키기 위해 미해결 문제를 숨기거나 완료 처리하지 않습니다.

## 압축 전달 형식

필요한 최초 요청·승인 범위·제약과 함께 다음만 전달하고, 후속 전달에는 이전 내용의 변경분만 씁니다.

- 결정 사항
- 미해결 문제와 필요한 판단
- 변경 파일과 편집 담당자
- 관련 검증 결과, 실패·미검증 항목, 증거 위치

전체 대화·전체 로그·프로젝트를 매번 복사하지 않습니다. 원문은 필요한 부분만 조회합니다. 승인 제한과 실패 사실은 압축 과정에서 빠뜨리지 않습니다. 담당자 자신의 의미 있는 질문·답변을 회의실에 직접 남기는 방식은 유지합니다.

## 이벤트 기반 진행

배정 후 총괄의 활성 턴에서 native wait_threads로 완료·실패·판단 요청을 기다립니다. 가능한 대상은 묶고 반환된 cursor를 사용합니다. 한 번의 대기는 최대 60초로 제한합니다. 시간초과만으로 진행 질문을 보내거나 전체 이력을 다시 읽지 않고 cursor를 유지하여 대기하거나 독립 작업을 합니다. 도구 자체의 이벤트 대기는 주기적 AI 진행 판단 요청과 구분합니다.

담당자의 최종 턴을 완료 이벤트로 받으면 별도 완료 통보 메시지를 또 보내지 않습니다. 작업을 막는 판단 요청은 필요한 대상에게 한 번 전달합니다. 주기적 AI heartbeat/cron은 만들지 않습니다. 일반 UI의 로컬 기록 갱신은 유지하되 AI를 호출하지 않습니다.

이미 종료된 총괄 턴을 자동으로 깨우는 기능은 호스트 지원이 실제로 확인된 경우에만 사용합니다. 지원이 확인되지 않았다면 활성 턴의 완료 대기를 사용하며, 종료 후에는 새 사용자/호스트 이벤트가 필요하다는 한계를 밝힙니다. 자동 재실행을 구현했다고 주장하지 않습니다.

## 변경 중심 검수와 로컬 도구

변경 diff, 직접 연결된 호출부·데이터 계약·관련 테스트·필수 프로젝트 지침부터 확인합니다. 공통 인터페이스 변경, 의존성 위험, 실제 실패나 설명되지 않는 동작이 있을 때만 이유를 밝히고 범위를 넓힙니다. 구현 후 관련 검증을 한 번 모아 실행하고 실패·후속 수정 영향 사례만 재검사합니다. 문서만 바뀐 경우 앱이나 Unity를 실행하지 않습니다.

파일 변경 확인은 git diff --name-only, 형식 확인은 git diff --check, JavaScript 문법 확인은 node --check를 사용합니다. 변경 관련 node --test 파일을 선택하며 저장소/브리지 변경에는 기존 npm test 규칙을 따릅니다. 레이아웃 변경은 scripts/check-layout.mjs로 확인합니다. 로그는 로컬에 두고 범위·결과·실패·증거 경로만 전달합니다. 같은 결과가 반복됐다는 이유로 AI나 회의를 호출하지 않습니다. 해석, 충돌, 예상 밖 실패, 승인 판단이 필요할 때 AI가 개입합니다.

규칙 적용을 위한 별도 상주 감시 프로그램은 만들지 않습니다. 실제 절감률은 측정 전에는 단정하지 않습니다. 적용 안내만을 위해 모든 담당자를 깨우지 않고 다음 필요한 업무 배정에 규칙을 포함합니다.
