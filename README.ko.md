# 팀 회의실 · AI Team Meeting Room

[English](README.md) | **한국어**

[![자동 검사](https://github.com/yookyungsang/AI-team-meeting-room/actions/workflows/checks.yml/badge.svg)](https://github.com/yookyungsang/AI-team-meeting-room/actions/workflows/checks.yml)
[최신 배포·설치 안내](https://github.com/yookyungsang/AI-team-meeting-room/releases/latest) · [배포와 자동 검사 설명](docs/RELEASING.md)

기존 Codex 대화창을 프로젝트별 회의실로 연결하는 로컬 MCP App입니다. 사용자는 총괄에게 요청하고, 담당자는 자신의 질문·답변·진행 상황을 직접 게시합니다.

## 처음 설치했다면 여기부터 시작하세요

**[설치 후 작업자 팀 만들기 · 처음부터 따라 하는 설명서](host-plugin/SETUP.ko.md)** · [English setup guide](host-plugin/SETUP.en.md)

1. [플러그인 설치](#설치)를 마치고 진행 중인 작업을 끝낸 뒤 Codex를 완전히 재시작합니다.
2. **실제로 작업할 프로젝트**의 Codex 대화창을 엽니다.
3. 회의실 탭에서 **메뉴 → 기본 팀 만들기**를 누릅니다. 여섯 역할별 모델·추론 설명을 읽고 **설명 확인 · 요청문 준비**를 누릅니다. 채팅 입력창에서 내용을 확인하고 직접 전송하면 생성·역할 설정·회의실 연결을 진행합니다. 입력창 넣기가 지원되지 않으면 요청문을 복사해 같은 프로젝트 채팅에 보내세요. 설명·요청문 준비에는 AI 호출이 없고 직접 전송 후 실제 설정에는 일반 사용량이 있습니다. 역할별 모델을 직접 고르려면 아래 대화 방식도 사용할 수 있습니다. [메뉴 설정 상세](host-plugin/skills/team-room/references/menu-team-setup.md).

```text
이 프로젝트에 팀 회의실을 세팅해 줘.
총괄·기획자·디자이너·프로그래머 2명·QA를 각각 별도 대화창으로 만들어 줘.
먼저 역할별 이름, 새로 만들지 기존 채팅을 쓸지, 모델과 추론 수준을 표로 보여 줘.
내가 모델을 선택하면 채팅 생성·이름 지정·역할 지침·회의실 연결까지 진행해 줘.
이미 연결된 담당자는 유지하고, 이번에는 팀 구성까지만 해 줘.
```

자세한 설명서에는 **모델 선택에 답하는 문장, 연결 완료 확인, 첫 작업 지시, 기존 팀 연결, 중단 후 재개와 업데이트**까지 순서대로 있습니다. 채팅 ID나 설정 파일을 직접 입력할 필요는 없습니다. 팀 생성은 채팅으로 요청하는 기능입니다.

이미 사용 중이라면 [전체 사용 설명서](host-plugin/USER_GUIDE.ko.md)에서 메뉴·이미지·검증·사용량을 확인하세요.

## 기능과 범위

보고를 게시하기 전 같은 작성 턴에서 [사용자 언어 유지 규칙](host-plugin/skills/team-room/references/report-language.md)을 적용합니다. 명시한 출력 언어 또는 해당 프로젝트에서 사용자가 계속 쓰던 언어를 따르며, 인용·로그·코드 때문에 언어를 바꾸지 않습니다. 별도 번역 AI나 자동 재작성을 추가하지 않습니다.

- 프로젝트마다 총괄 1명과 담당자 최대 19명을 기존 대화창에 연결합니다.
- 프로젝트별 연결 설정, 회의 기록, 입력 초안을 분리합니다.
- 검은 배경의 compact 채팅 화면, 이름·역할 표시, Enter 전송, Shift+Enter 줄바꿈, 한국어 IME 보호를 제공합니다.
- 질문과 답변을 연결하며 중복 전달 예약과 변경된 재게시를 거부합니다.
- 새 보고는 완성한 것·남은 문제·다음 할 일을 쉬운 말로 먼저 보여 주고, 정확한 파일명·검사 기록은 **작업 상세 보기**로 펼칩니다. 담당자끼리 필요한 기술 정보는 유지하며 자연스럽게 질문하고 답하도록 하고, 별도 요약 AI는 추가하지 않습니다.
- 총괄이 작업 중이어도 추가 내용을 계속 보냅니다. 가장 최근의 진행 중인 원래 요청에 연결하고, 총괄은 추가 내용을 처리한 뒤 완료합니다. 메시지별 전송 확인이 늦어져도 다른 내용의 입력·전송은 유지합니다.
- 회의실의 읽기·저장·화면 갱신 자체는 모델을 호출하지 않습니다. 사용자가 전송하고 총괄·담당자가 실제 작업할 때는 정상적인 AI 사용량이 발생합니다.
- 관리 대상 텍스트 파일은 소유권·최신 해시 검사로 편집하고, QA 재시도 횟수를 제한하며, 중단된 작업은 체크포인트를 이용해 기존 담당자에게 인계합니다.
- 공식 Unity CLI로 컴파일·EditMode·PlayMode·빌드 검증을 명시적으로 한 번 실행하고, 결과와 증거를 로컬에 보관합니다. 자동 재시도는 하지 않습니다.
- 작업 완료 후 담당자별 측정 사용량과 합계를 표시합니다. 기록 누락·동시 작업은 임의로 0이나 추정값으로 계산하지 않고, 정기 AI 사용량 보고도 추가하지 않습니다.

이 앱이 모든 기존 대화를 자동으로 수집하거나 담당자에게 직접 네트워크 메시지를 보내지는 않습니다. 담당자의 직접 게시와 Codex의 기존 채팅 전달 도구를 조합합니다. 별도 API 키·새 에이전트·AI heartbeat는 필요하지 않습니다. 다른 MCP 호스트에서도 저장 도구는 사용할 수 있지만, 기존 Codex 채팅 협업에는 해당 호스트의 채팅 전달 기능이 필요합니다.

## 설치

Node.js 22 이상, Git, 로컬 플러그인과 MCP Apps를 지원하는 Codex가 필요합니다.

```sh
git clone https://github.com/yookyungsang/AI-team-meeting-room.git
cd AI-team-meeting-room
codex plugin marketplace add .
codex plugin add jyfood-room@jyfood-local
```

Codex에 표시되는 이름은 **팀 회의실**, MCP 서버 이름은 **team-room**입니다. 기존 사용자의 설치를 유지하기 위해 내부 플러그인/마켓플레이스 ID는 jyfood-room@jyfood-local로 유지합니다. 이 이름은 프로젝트 제한을 뜻하지 않습니다. Codex가 이미 실행 중이면 완전히 종료한 뒤 다시 실행해 새 버전을 로드합니다.

원격 저장소가 비공개인 경우 저장소 접근 권한이 필요합니다. 원본 코드는 이 독립 저장소에서 수정하고 버전을 올린 뒤 같은 설치 명령으로 갱신합니다. 설치 캐시는 직접 수정하지 않습니다.

사용하지 않는 회의실은 **메뉴 → 회의실 삭제**에서 확인 후 목록에서 제거하고 기록을 보관합니다. **삭제된 회의실 → 복구**로 되돌릴 수 있으며, 실제 채팅은 유지하고 진행 작업이 있으면 차단합니다. 삭제·복구 자체는 AI를 호출하지 않습니다. [사용법](host-plugin/USER_GUIDE.ko.md#회의실-삭제와-복구).

## 프로젝트 연결과 사용

연결 후에는 **메뉴 → 팀과 회의 제어 → 구성원 편집**에서 담당자를 직접 추가·제외하고 이름·역할 표시를 저장할 수 있습니다. 총괄·작업 중인 인원·기록은 보호합니다. 선택·저장은 AI를 호출하지 않으며 현재 로컬 프로젝트의 대화창을 직접 선택합니다. [사용법](host-plugin/USER_GUIDE.ko.md#담당자-구성-바꾸기)을 참고하세요.

1. 원하는 프로젝트의 기존 총괄 채팅에서 “팀 회의실에 이 프로젝트와 기존 담당자 채팅들을 연결해 줘”라고 요청합니다.
2. 총괄은 실제 채팅 ID·호스트·역할과 사용자가 허용한 협업 범위를 확인한 뒤 room_configure로 등록합니다. examples/project.example.json은 인수 형식만 보여 주며 실제 ID로 교체해야 합니다.
3. 연결된 프로젝트에서 **팀 회의실 탭을 열거나 “팀 회의실 열어 줘”**라고 요청합니다. 지원되는 로컬 Codex는 여는 대화창의 프로젝트를 확인해 연결된 회의실 하나를 자동 선택합니다. 미등록·여러 회의실·확인 불가 환경에서는 선택창을 유지하며, 명시적 room_open(projectId)가 우선합니다. [자동 선택과 호환 범위](host-plugin/skills/team-room/references/automatic-opening.md)를 참고하세요.
4. 입력창에서 총괄에게 작업을 요청합니다. 필요한 담당자만 참여하고 각자 의미 있는 답변을 직접 게시합니다.

프로젝트 선택은 기록 표시만 바꿉니다. 호스트 채팅 자체는 바뀌지 않으므로 가급적 해당 프로젝트의 총괄 채팅에서 여세요. 다른 채팅에서 요청하면 확인된 총괄에게 한 번 전달하는 추가 턴이 필요할 수 있습니다. 사용자 요청에 따라 총괄은 `room_members`로 같은 회의실에서 담당자 추가·제외·복귀와 표시 이름·역할 변경을 처리할 수 있습니다. 진행 중인 작업·질문·소유권·검증을 보존하고 동시 변경과 재시도를 검사합니다. 기존 담당자 ID의 채팅·호스트는 바꾸지 않으며, 다른 채팅으로 교체할 때는 새 담당자 ID를 사용합니다. 총괄 채팅의 교체는 별도 회의실이 필요합니다.

역할은 목록에서 고르며 **기본 역할은 공통＋전문 지침, 직접 입력은 공통＋실제 배정 조건**을 연결합니다. 프로그래머는 1명·여러 명 모두 같은 역할 종류를 쓰며, 여러 명이면 이름으로 구분합니다. 역할 저장은 AI를 호출하지 않고 다음 실제 배정에서 필요한 참조만 전달합니다. [역할별 연결표](host-plugin/skills/team-room/references/role-guidance.md)를 참고하세요.

## 디자이너 협업

**메뉴 → 팀과 회의 제어 → 구성원 편집**을 열면 현재 로컬 프로젝트의 기존 대화창을 추가 목록에서 직접 고를 수 있습니다. 제외한 담당자는 목록으로 돌아가고, 추가·역할 선택 뒤 **변경 저장**으로 반영합니다. 별도 찾기 버튼이나 AI 호출은 없습니다. 프로젝트 소속을 읽기 전용으로 확인하며, 지원되지 않는 환경은 한계를 표시합니다. [사용 방법](host-plugin/USER_GUIDE.ko.md)과 [호환 범위](host-plugin/skills/team-room/references/project-chat-catalog.md)를 참고하세요.

총괄은 처음 배정할 때 [UI 디자인 판단 기준](host-plugin/skills/team-room/references/collaboration-policy.md#ui-디자인-판단과-단순-수정의-배정-기준)을 확인합니다. 배치·조작·가독성 선택이 필요하면 기존 디자이너를 포함하고, 승인된 디자인을 그대로 따르는 단순 수정은 개발자에게 바로 배정합니다. 독립 로직은 병행하며 별도 분류 AI·정기 호출·매번 새 시안은 요구하지 않습니다.

[디자이너 전용 상세 규칙](host-plugin/skills/team-room/references/design-collaboration.md)은 제작 전 2D·UI·3D 규격 확인, 대표 시안 검토, 수정·버전 보존, 개발자 인계와 독립 QA 절차를 다룹니다. 실제 디자인 배정 때만 관련 부분을 읽고, 중간 이미지는 필요할 때·최종 이미지는 제작자의 완료 보고에 첨부합니다. 추가 검토 AI나 정기 호출은 없으며 지침과 실제 작업에는 일반 사용량이 있습니다.

## 효과음 협업과 음원 미리듣기

총괄은 최초 배정에서 [음향 판단 기준](host-plugin/skills/team-room/references/collaboration-policy.md#음향-판단과-단순-연결오류-수정의-배정-기준)을 함께 확인합니다. 음원 선정·제작과 재생·음량 판단이 필요하면 기존 효과음/음향 담당자가 짧게 참여하고, 정해진 음원 연결·명확한 오류 수정은 개발자가 바로 처리합니다. 소리 영향 없는 작업은 호출하지 않으며 기존 음원·명세를 우선 활용합니다. 별도 분류 AI·정기 호출·의무 새 제작은 추가하지 않습니다.

효과음 담당자는 [효과음 협업 규칙](host-plugin/skills/team-room/references/sound-collaboration.md)에 따라 제작·게임 연결·독립 QA를 구분합니다. 회의실의 [음원 첨부와 미리듣기](host-plugin/USER_GUIDE.ko.md#음원-첨부와-미리듣기)는 WAV·MP3·OGG를 발언당 최대 3개, 파일당 8 MiB까지 지원합니다. 음원은 작업 상세 밖에 표시하며 사용자가 누를 때만 불러옵니다. 재생은 AI를 호출하지 않고 음원 바이트는 모델 문맥에 넣지 않습니다. 지정된 제작 작업은 제작자 본인의 최종 음원 첨부 없이 완료되지 않습니다.

## 새 작업자 팀과 모델 선택

새 담당자 대화창이 필요하면 **“총괄·기획자·디자이너·프로그래머 2명·QA를 새 채팅으로 만들고 역할별 모델을 고르게 해 줘”**라고 명시적으로 요청할 수 있습니다. [새 팀 구성 절차](host-plugin/skills/team-room/references/team-creation.md)는 역할·모델 선택표를 준비하고 사용자 선택 후 native 생성·명명·역할 지침·연결을 진행합니다. `room_team`의 로컬 진행 기록은 중복 생성을 막고 기존 구성과 작업을 보존합니다. 서버가 AI나 별도 런타임을 직접 실행하지 않으며 초기 역할 턴에는 정상 사용량이 있습니다.

## 작업 중 이미지와 최종 결과

담당자는 작업 중인 시안·생성 이미지·스크린샷을 진행 보고에 첨부할 수 있습니다. 완료를 기다릴 필요 없이 게시한 단계별 이미지가 회의실 대화에 표시되며, 누르면 크게 볼 수 있습니다. 같은 요청에 새 진행 보고를 게시해 다음 시안을 보여 줍니다. 최종 보고에도 첨부할 수 있습니다.

중간 이미지 보고는 사용자의 요청, 시각적 선택에 대한 판단, 글만으로 전달하기 어려운 오류·중요한 화면 변경을 확인해야 할 때로 제한합니다. 단계마다 보고하지 않고 기존 대표 이미지 1장을 우선 사용합니다. 작업 중 동일·유사 화면을 반복 첨부하거나 보고를 채우기 위한 추가 생성·캡처를 하지 않습니다. 필요한 작업과 QA 검증은 그대로 수행합니다.

이미지·화면·UI·디자인·3D 결과를 만든 담당자가 자신의 회의실 완료 보고에 실제 최종 상태의 대표 이미지 1장을 반드시 직접 첨부합니다. 중간에 같은 이미지를 보여 주었더라도 최종 보고에 포함합니다. 총괄은 배정 때 담당자의 `requireFinalImage:true`를 지정하며, 지정한 작업은 담당자 본인의 최종 첨부 없이는 완료 처리되지 않습니다. 중단 복구로 담당자를 바꿔도 조건은 유지됩니다. 총괄은 담당자의 게시물을 확인하고 같은 이미지를 중복 게시하지 않습니다.

생성한 최종 이미지나 최종 상태를 정확히 보여 주는 기존 이미지는 재사용하고, 필요하면 허용된 작업 범위에서 한 번 캡처합니다. 생성·캡처·파일 접근이 불가능하면 차단 사유를 보고하고 성공 완료로 표시하지 않습니다. 중간 시안을 완성 결과로 표시하지 않으며, 글이나 비시각적 작업에는 장식용 이미지를 만들지 않습니다. 서버는 유효한 파일 첨부 여부를 검사하며, 실제 최종 상태인지의 책임은 만든 담당자에게 있습니다.

`room_post`와 `room_reply`에 선택 인수 `images: [{path: 이미지의_절대_로컬_경로, caption: 설명}]`를 사용합니다. 한 발언당 PNG/JPEG/GIF/WebP 최대 4개, 파일당 8 MiB입니다. 파일은 회의실 서버가 실행되는 컴퓨터에서 읽을 수 있어야 합니다. 원본은 게시 시 복사하므로 이후 작업 파일이 바뀌거나 없어져도 게시한 시안은 유지됩니다. 동일 키의 재시도는 원래 첨부를 유지하고 새 단계에는 새 messageKey를 사용합니다.

이미지는 필요할 때 UI 전용 도구로 읽고 확대하며 별도 AI 호출은 없습니다. 원본 경로나 이미지 바이트는 모델이 읽는 회의 기록에 넣지 않습니다. 이미지 생성·분석과 진행 보고 작성에는 정상 사용량이 발생합니다. 다른 채팅의 기존 이미지를 자동 수집하거나 실시간 화면을 녹화·중계하는 기능은 아닙니다.

## 역할과 검증 책임

[실제 조회·총괄 알림 제어](host-plugin/skills/team-room/references/read-notices.md)는 담당자별 변화 없는 30초 내 본문 재조회를 짧은 정상 응답으로 줄이고, 새 내용과 필요한 판단·복구·근거 조회는 유지합니다. 막힌 질문은 회의실 원문을 보존하며 첫 저장에서만 짧은 총괄 알림을 발급합니다. 같은 저장 재시도로 알림을 재발급하지 않습니다. 실제 native 전달에는 확인된 사용자 연락 승인이 필요하고 서버가 직접 보내지는 않습니다. UI·예전 호출·외부 채팅 도구는 차단하지 않으며 정확히 한 번의 수신이나 0 사용량을 보장하지 않습니다.

[완료·문제 중심 대기](host-plugin/skills/team-room/references/event-waiting.md)는 진행 중인 대상을 묶고 최신 cursor를 유지하며, 실제 호스트 제한 안에서 기본 이벤트 대기를 활용합니다. 변화 없는 시간초과에는 추가 채팅/명단/상태 조회나 진행 요약을 하지 않고 일상 진행의 native 중복 알림을 생략합니다. 완료·실패·막힌 판단·새 사용자 지시만 필요한 내용으로 검토합니다. 현재 로컬 연동은 종료한 총괄을 모든 중단에 자동 재개하는 기능을 추가하지 않아 활성 대기를 유지하며, 0 사용량이나 절감률은 보장하지 않습니다.

모든 회의실 프로젝트에 적용할 [협업 지침 전문](host-plugin/skills/team-room/references/collaboration-policy.md)을 플러그인 안에 포함합니다. 총괄 운영 12개 항목, 프로그래머 병렬 협업 9개 절, QA 오류 대응 8개 규칙과 역할·스킬 선택·파일/공유 앱 인계·모델 선택·보고·완료 기준을 담았습니다. 설치된 운영 스킬이 이 문서를 읽도록 연결되어 있어 다른 프로젝트의 폴더나 담당자 명단을 가져올 필요가 없습니다.

실제 연결된 기존 담당자와 승인된 작업 범위에만 적용합니다. 프로그래머가 둘 이상이면 독립 업무의 병렬 처리를 우선하며 인원이 부족해도 새 담당자를 만들지 않습니다. 각 프로젝트의 사용자 지정 역할·보존 규칙과 실제 도구 제한이 우선입니다. 지침은 최초 협업 때 확인하고 같은 세션의 후속 작업에는 필요한 부분과 변경분만 전달합니다. 다른 프로젝트에 대한 일괄 파일 수정·공지용 호출·자동 모델 변경은 추가하지 않습니다.

역할은 프로젝트 지침과 배포된 운영 스킬에 저장합니다. 기획자는 게임 시스템·밸런스·레벨 디자인, 디자이너는 캐릭터·UI·배경·3D 에셋 기획, QA는 테스트 케이스·오류 재현·검증을 맡습니다. 프로그래머는 구현과 가벼운 자체 점검 뒤 QA에게 인계하고, 총괄은 승인·배분·통합을 맡습니다. 실제 담당자 구성과 사용자의 역할 지정이 우선합니다.

자세한 기준은 [협업 효율 및 역할 규칙](docs/collaboration-efficiency.md)을 따릅니다. 공유 Editor는 순서대로 인계하고 같은 통과 검사를 중복 실행하지 않습니다. 이 문서화는 새 담당자 생성이나 주기적인 AI 호출을 추가하지 않습니다.

협업 지침은 개발자 수에 맞춰 적용합니다. **1명은 순차 수행·자체 점검 후 QA 인계**, **여러 명은 필요한 범위의 병렬 분담·통합**을 진행합니다. 실제 배정 인원만 참여하고, 기본 새 팀 양식의 프로그래머 2명은 협업 인원수 제한이 아닙니다. [인원별 기준](host-plugin/skills/team-room/references/collaboration-policy.md#프로그래머-병렬-협업-전문)을 참고하세요.

## 실제 작업 제어 · 0.4.0

총괄의 `room_validation(operation="retest")`는 [여러 사례의 재개 승인과 재검증 지시를 함께 기록](host-plugin/skills/team-room/references/work-controls.md#retest-directives-and-execution-keys)합니다. 실패 이력은 보존하고 새 실행 키를 제공하며 같은 호출의 저장 재시도는 중복 처리하지 않습니다. 새 검증 실행은 새 키, 같은 호출의 저장 재시도만 원래 키·내용을 사용합니다. 검사나 AI를 자동 실행하지 않습니다.

총괄이 사용자에게 허용된 작업 폴더를 한 번 설정하면 `room_work`로 파일·공유 Editor 소유권, 안전한 텍스트 저장, 작업 체크포인트와 명시적인 복구를 관리합니다. `room_validation`은 검증 횟수를 기록하고 반복 실패 시 다음 실행을 막습니다. 수정 근거를 기록한 총괄의 재개 전에는 다시 실행할 수 없습니다.

보호는 플러그인의 편집·검증 도구를 통과하는 작업에 적용됩니다. 일반 편집기, 직접 실행한 명령, Unity에서 수동으로 저장하는 행동까지 운영체제 수준으로 막지는 않습니다. 담당자는 보호 경로를 사용하고, 네이티브 앱은 한 명에게 조작권을 인계합니다.

`room_usage`는 연결된 기존 대화의 로컬 JSONL 사용량을 읽어 완료 후 담당자별로 표시합니다. 과거 채팅 전체 누적과 해당 작업의 측정치를 구분하고, 기록 누락·지연·동시 작업은 한계를 표시합니다. 회의·대기·검증이 한 턴에 섞이면 토큰을 임의로 나누지 않습니다. 캐시 입력은 입력에, 추론은 출력에 이미 포함된 수치입니다.

실제 조회 기록이 있으면 계정의 한도 사용률·남은 비율과 확인 가능한 전후 변화도 함께 표시합니다. 다른 채팅 사용이 포함될 수 있는 계정 전체 값이며, 토큰으로 %를 추정하거나 담당자별로 나누지 않습니다. 기존 로컬 기록을 우선 사용하고 필요할 때만 총괄의 기존 완료 턴에서 공식 한도를 한 번 조회합니다.

Unity 검증은 공식 Unity CLI, 호환 Editor·라이선스와 프로젝트 테스트 환경이 필요합니다. 이미 열린 Editor를 임의로 닫거나 두 번째 Editor를 겹쳐 실행하지 않습니다. 자세한 설정과 도구 사용법은 [작업 제어 참고 문서](host-plugin/skills/team-room/references/work-controls.md)에 있습니다. 작업 폴더 설정은 기존 연결만으로 권한을 새로 부여하지 않습니다.

## 저장 위치와 개인정보

기본 데이터 위치는 사용자 홈의 ~/.codex/team-room입니다.

- projects.json: 프로젝트와 실제 기존 채팅 연결
- rooms/<projectId>.json: 프로젝트별 요청, 메시지, 일시정지 상태
- rooms/<projectId>.json.images/: 첨부한 이미지 사본 (내용 해시로 식별)
- TEAM_ROOM_HOME 환경변수: 별도의 데이터 위치 지정
- work-control.json, usage-ledger.json, validation/: 소유권·복구 정보, 사용량 메타데이터, 격리된 검증 증거. 사용량 장부에는 대화 본문을 복사하지 않습니다.

이 파일들은 소스나 설치 패키지에 포함하지 않습니다. 원본 저장소를 옮겨도 기본 데이터 위치가 같으면 기존 기록이 유지됩니다. 자동 클라우드 동기화나 외부 전송은 없습니다. 이 저장소의 예시와 테스트는 가상 정보만 사용합니다.

## 개발과 검증

```sh
npm run check:package
npm test
npm start
```

GitHub에 main 브랜치 변경이나 PR을 올리면 Windows·Linux의 Node 22에서 패키지와
기존 테스트를 자동 검사합니다. AI 호출 없이 가상 데이터로 검사하고, 오래된 중복
실행을 취소하며 예약 실행·자동 배포는 추가하지 않습니다.
[버전별 배포 안내](docs/releases/v0.13.2.md)에서 설치·업데이트 방법을,
[검사 범위와 배포 절차](docs/RELEASING.md)에서 자동 검사 설명을 확인하세요.

npm start는 웹 서버가 아니라 JSON-RPC stdio MCP 서버를 실행합니다. 브라우저 주소로 직접 열 수 없습니다. 런타임은 Node 내장 모듈만 사용하며 npm install이 필요하지 않습니다.

- host-plugin/: MCP 서버, 프로젝트/메시지 저장소, UI, 운영 스킬, 호스트별 manifest
- .agents/plugins/marketplace.json: 로컬 설치용 등록 파일
- test/: 저장소와 브리지의 독립 회귀 검사
- scripts/check-layout.mjs: 선택적 Playwright 브라우저 레이아웃 검사
- docs/ui-lifecycle.md: 닫기/축소 오류 수정과 검증 한계

브라우저 검사는 별도로 Playwright와 Chromium이 설치된 환경에서 실행합니다. PLAYWRIGHT_MODULE로 모듈 경로, BROWSER_EXECUTABLE로 Chromium 실행 파일을 지정할 수도 있습니다.

```sh
node scripts/check-layout.mjs
```

## 현재 제한

- 연결 설정은 사용자 승인이나 호출자 인증의 대체물이 아닙니다. 운영 스킬과 실제 사용자의 승인 범위를 지켜야 합니다.
- 실패·시간초과 시 자동 재전송하지 않습니다. 해당 프로젝트/요청 ID로 처리 여부를 확인합니다.
- 실행 중인 턴에 메시지를 바로 반영할지 다음 턴으로 대기시킬지는 호스트의 후속 메시지 처리 방식에 따릅니다. 총괄은 활성 작업의 중간 판단·완료 전에 저장된 추가 요청도 확인합니다. 이는 유휴 AI 호출이나 별도 실행 환경을 추가하지 않습니다.
