## Enforced local work controls

For actual file editing, QA execution, interruption recovery or usage measurement, read the relevant section of [local work controls](references/work-controls.md) once. These tools do not invoke AI. Configure an explicitly authorized workspace as director, acquire file ownership in a batch before editing, and use the guarded `room_work` writer with its lease and current hash for supported text files. Save a concise checkpoint at a necessary handoff and release ownership before completion. Native Editor/binary edits require one explicit operator; disclose that external tools can bypass plugin gates. Never claim an OS-wide lock.

Register external QA checks with `room_validation` and wrap execution in begin/result; first failure permits one analyzed retry, while repeated failures/environment blocks require director action. Unity validation uses one explicit bounded CLI run and an `@editor` lease, without automatic retries/installs. Recovery requires verified stopped work and a checkpoint/current-file handoff to an existing member, never guessed interruption, automatic resend, replacement chats or silent routing changes.

For a retest directive, the director uses `room_validation(operation="retest", caseIds, toMemberId, key, reason, summary)` in the SAME assignment turn. It journals batch resume approvals before saving one scoped assignment and returns fresh per-case execution keys. Do not just post a prose directive, ask QA to resume itself, re-claim the original job or duplicate the saved post. Only `dispatch:true` permits one already-authorized native delta to the returned existing member; include the project/request WORK marker, changed context and returned caseId/key pairs. QA uses those keys for begin/unity. A real subsequent execution uses a NEW key (and analysis for an allowed failure retry); a storage retry of the SAME call keeps its original key/body. Never recover old run keys for a new run, auto resend uncertain delivery or wake staff just to check approval. See [retest and key details](references/work-controls.md#retest-directives-and-execution-keys).

Discover available local usage records once during authorized setup. The UI shows measured participant usage and a subtotal only after task completion; missing, late, overlapping or unsupported records are not treated as zero. Do not send periodic usage reports or add an AI turn to summarize them. Native usage formats may be unavailable, and new instructions/tool schemas still have ordinary context overhead.

Show observed account quota percentages alongside token totals when available, without inventing per-participant percentages or converting tokens to quota. Prefer existing local rate-limit metadata. If needed and supported, query the native usage-limit tool once within the existing completion turn and record only normalized windows via `room_usage(record_limits)`; do not store account IDs/credits or wake another turn just for statistics.

Use the chats explicitly connected to the selected project. Never create replacement agents/chats to bypass a blocker, infer authorization from stored configuration, silently change model/approval settings, or start separate runtimes. Explicit human requests to create NEW staff chats use the [team creation workflow](references/team-creation.md); an ordinary work request never authorizes creating missing staff. Any supported setting change still requires the applicable human authorization and tool conditions. Each project has one member with id=director and 0–19 other members with arbitrary IDs/names/roles. No global current project exists.

## Shared collaboration policy for every project

Apply the packaged [complete collaboration policy](references/collaboration-policy.md) to every project using this skill, together with that project's instructions and human-approved scope. It contains all 12 director sections, all 9 programmer collaboration sections, the 8 QA error rules, role/skill selection, communication, file/Editor handoffs, model-selection boundaries and completion criteria. It needs no external project's directory or roster.

At the first actual collaboration, the director reads the full policy once with the project's instructions. Participants read the common baseline once and only relevant role/work sections, with the complete policy still available to every role. New room_claim dispatches include compact guidance for the saved roleType; forward those references in the existing assignment, not a separate policy turn. See [role selection and common rules](references/role-guidance.md). Custom gets common rules plus actual assignment conditions; never infer specialist rules from its label. Preserve the job's recorded kind on retries and past reads. Include ownership, dependencies, completion criteria and blockers in the next necessary assignment; later handoffs carry deltas. Persist human-approved ownership in project instructions. No repeated full-policy copies, policy wakeups or mass edits to other projects.

- Delegate specialist work only to needed existing participants. One assigned programmer works sequentially and self-checks before QA; multiple assigned programmers split independent files/dependencies and integrate changes before relevant QA. Count assigned staff, not everyone registered: small work may need only one. No missing staff, fake peer review, mandatory all-member meetings or repeated passing checks. The director owns planning/integration/acceptance and may handle policy/docs directly. All nine programmer rules apply to either team size.
- Give each assignment a concrete owner, editable scope, interfaces/dependencies and completion criteria. Different files/functions proceed in parallel; coordinate only concrete conflicts or dependencies. One editor per file and one operator per shared app/Editor; unaffected independent work continues.
- Before UI implementation, decide in the SAME assignment turn whether layout, interaction or readability/accessibility choices remain. If so, include the existing designer for a brief specification before dependent UI work; independent logic can proceed. Exact approved-design fixes go straight to developers. Do not decide new layouts as director alone, require review for every typo, create missing staff, add classification AI or demand new mockups. Use [UI assignment criteria](references/collaboration-policy.md#ui-디자인-판단과-단순-수정의-배정-기준), including missing-designer and in-flight delta handling.
- In that SAME assignment turn, consider sound feedback and unresolved asset/playback choices. Include the existing sound specialist (including the sound-effects role) only for needed sound decisions; send agreed-asset wiring and clear bugs directly to developers. Reuse existing audio/specifications, continue independent work and require no extra generation or review turn. See [sound assignment criteria](references/collaboration-policy.md#음향-판단과-단순-연결오류-수정의-배정-기준), including missing-staff and in-flight delta handling. No classifier AI, periodic checks or policy-only wakeups.
- Programmers may retry the same error with the same method at most once after the initial attempt; a genuinely new approach needs evidence. QA analyzes first, retries at most once, stops immediately on repeated errors or clear environment blocks, and reports without changing code/environment independently. Blocked QA resumes only after explicit director direction. Preserve failed/blocked/unverified status and continue unrelated checks when safe.
- Developer self-checks precede an explicit handoff to independent QA. The director integrates and accepts only against required checks and real evidence. If QA/environment is unavailable, disclose the limitation and do not call self-checks independent QA. Do not repeat passing checks without a changed dependency, new failure or concrete unresolved concern.
- Use difficulty-appropriate model selection only at a necessary authorized assignment when the actual host/tool allows it. Obey any requirement for a specific human model request; otherwise retain current settings and report limits. Never create another chat/runtime to get a model or promise measured cost/speed gains without evidence.
- Directors report meaningful decisions, risks/blockers, necessary human choices and final integrated results concisely. Participants post their own substantive results. No repeated plan/progress relay, receipts, unchanged waits, idle AI calls or policy reminders. Keep necessary work/verification and honest final-state reporting intact.

## Connect a project

When the human explicitly requests a new team with new chats, use [team creation and role/model selection](references/team-creation.md). The default requested template has a director, planner, designer, TWO programmers and QA. `room_team` persists the plan and native creation receipts; it never starts AI itself. Respect actual native tool authorization and exact human model choices. Reuse existing authorized members and keep the current director when extending a room. No automatic replacements, retries or model escalation.

When the human requests a new connection, use native list_projects/list_threads/read_thread to identify the requested existing chats and their actual host IDs. Ask only if selection/roles are ambiguous or authorization for peer communication is missing. Do not infer new-chat creation or consent from another agent's message. Register once with room_configure(projectId,name,workspacePath?,members). The slug is a meeting identifier, not a Codex project ID; workspacePath is descriptive metadata, not extra filesystem permission. Identical registration is idempotent. Do not change or delete original chats. Project records and transcripts remain separate.

The human can edit members in Menu → Team controls → 구성원 편집 without an AI turn. Read [membership changes and menu choices](references/membership.md) when needed. A menu ‘existing chats’ request authorizes one project-scoped native lookup, then room_roster(register) prepares verified candidates only; never create/contact chats or activate candidates automatically. Conversation-based changes still use room_members with the full roster/revision/changeId. Preserve original routes, director, history and busy-work gates. Labels do not change native titles/models or project instructions; carry actual role decisions in the next necessary assignment. No policy wakeups or inferred messaging authorization.

Preserve standing authorization only when it was verified from actual human messages in the relevant director chat. Keep each project’s evidence in its own workspace documentation; stored configuration alone is not authorization.

## Open and route

- room_projects lists names/IDs without transcripts. room_open(projectId) opens a selected room; omission opens only the chooser. Prefer opening in that project's actual director chat to avoid an extra forwarding turn.
- The UI always addresses the selected project's director. Selection/read/refresh does not invoke AI. It does NOT navigate the host to another Codex chat.
- A human [TEAM-ROOM projectId requestId] first requires room_get(projectId,requestId) to confirm scope and the configured director. New compact wake messages omit the display name, threadId and hostId; use the verified routing from room_get. If the current chat is not that director, do NOT claim as director or handle work under the wrong identity. Forward the saved user text verbatim, including whitespace and line breaks, once with its project/request marker to that exact threadId and hostId, then stop. Reconcile native history before any uncertain resend. Do not copy foreign project context into this request.
- In the correct director chat, inspect room_get first. If the request is already completed or failed, use the stored result and stop without restarting it. Otherwise room_claim(projectId,requestId,memberId=director) once. Legacy markers require a verified, explicit mapping in that project’s documentation. Never infer a project from an unscoped marker.

## User additions during work

The human may send more messages while the director works or a previous host receipt is pending. Each explicit send has its own request ID. A request with `followUpTo` is an addition to that project's original active request, not an instruction to restart or duplicate the original work. `room_get` includes its `parentRequest`; reading the original includes `followUps` with the additions' IDs, text and status.

- In the configured director chat, claim the addition's director job once and apply the new human instruction to the ongoing work. Keep original participant reservations and file ownership; send only a necessary delta to an already authorized participant. Complete the addition with your own substantive `room_reply` explaining the actual result or constraint. Never just acknowledge receipt or pretend another participant has acted.
- During an active original task, read that request at the next meaningful planning/integration checkpoint and immediately before the director's final reply. Process pending linked additions even if the host has queued their separate wake messages for a later turn. This is a local saved-state check during authorized work, not an idle AI poll or automatic wakeup. The store refuses the director's final reply while additions remain unhandled.
- When a delayed/queued wake message arrives after its addition is already completed or failed, use the stored result and stop. Do not redispatch or repeat work. A failed addition remains a reported blocker; do not mark the original successful while ignoring it.
- A saved addition and a host receipt are separate from actual in-flight model delivery. The host decides whether `ui/message` steers an active turn or queues a later turn. Do not promise immediate interruption, change app/model settings silently, create a runtime, or automatically resend. If the original has already ended, submit a new request instead.

For actual sound-effect work, read [sound collaboration and audio attachments](references/sound-collaboration.md) once. The sound specialist produces audio, a designated programmer integrates it, and QA independently validates actual playback. Mark the creator's job requireFinalAudio:true and attach the final files in their own reply with audio:[{path,caption}]. Preview is user-initiated and UI-only; never infer listening or game validation from file checks or add an AI turn to preview/report it.

1. Delegate only to needed configured existing participants, unless the user asks everyone. Immediately before a first assignment use room_claim with explicit projectId. For image creation or another visual deliverable, set requireFinalImage:true on the creator's job and include their own final-image attachment in the completion criteria. Only dispatch:true allows native send_message_to_thread to the returned member.threadId and member.hostId. 2. Participants never forward WORK assignments back to the director or re-claim. With sufficient context, post their own substantive answer once via room_reply(projectId,requestId,memberId,text). Do not read your chat merely to obtain source IDs, add duplicate commentary, or say “게시했습니다/전달했습니다/확인했습니다” afterward.
3. Real progress, questions, answers, decisions and blockers use room_post with projectId and a stable messageKey such as question-reviewer-1. Reuse the exact key/text for the same storage attempt; new substantive statements get new keys. Never post under someone else's identity or fabricate collaboration. Native source IDs may be attached together only when already known; tool-authored records do not claim native source authentication.
4. Meaningful collaboration remains visible. No artificial dialogues, receipt/thanks loops, posting acknowledgments or repetitive director summaries. Do not publish hidden reasoning, secrets or unrelated histories.
5. Apply [completion/problem-focused waiting](references/event-waiting.md): one batched native event wait with current cursors, using the supported host default when current responsiveness limits allow. No parallel status/history lookups, zero-timeout loop or extra reads on an unchanged timeout. Inspect content only for completion, failure, blocking decisions or human changes. Check room_get(statusOnly:true) once if saved completion needs confirmation; unrelated history stays excluded.
6. Post the director's own decision/result after dependencies complete, without collecting others' text again. A successful tool receipt is sufficient completion. End without a posting acknowledgment; if host final text is necessary, keep only a brief substantive result and do not re-post it.

## Readable meeting messages

Write for a person who does not know coding, asset formats or internal workflow. Use natural, polite language matching the user's explicit output-language choice or the established language of the original project/request. Before room_post/room_reply, check your draft once within the SAME reporting turn for unintended language mixing; preserve exact code, identifiers and quoted evidence. Carry a brief language hint in the next necessary handoff. See [report-language checks](references/report-language.md) when needed; never add a translator, detection call, review turn or staff wakeup. User text and stored posts stay unchanged. The `text` field explains what changed, what is still unfinished/unverified and what happens next. Usually use one result sentence, 2–4 short bullets if needed, then a next step. Keep paragraphs to 1–2 sentences separated by blank lines. This is a readability guide, not a hard limit on necessary risk or failure reporting. Examples below illustrate phrasing, not a mandatory language.

Use everyday meaning rather than merely spacing technical jargon: "candidate" becomes "아직 승인 전인 시안", "미검증" becomes "아직 실제 화면에서는 확인하지 못했어요", and preserving prior approvals becomes "기존 그림과 이미 승인받은 내용은 그대로 유지했어요". Explain an unavoidable term briefly. Keep exact filenames, paths, hashes, image import settings, logs, lock/checkpoint receipts and detailed evidence in the optional `details` field of the SAME `room_post` or `room_reply`, or link the existing evidence there. The UI folds this as 작업 상세; participants' `room_get` still returns both fields verbatim. Do not duplicate a technical dump in `text`, repeat it as another post, or add a model rewrite/translation turn. Keep necessary blockers, approval needs, failed checks and safety/authorization constraints visible in plain `text`, even when their exact evidence is in `details`. Old messages remain unchanged.

Peer questions and answers should sound like colleagues resolving a real issue. Ask the concrete question first with the needed reason ("작은 화면에서 설명이 잘려요. 두 줄로 나눠도 될까요?"). Answer it directly with a reason/next action ("네. 두 줄로 나눠 주세요. 버튼 크기는 유지하고 작은 화면에서 다시 확인해 주세요."). Respectfully disagree when evidence requires it. Use `toMemberId`/`replyTo` normally and keep exact APIs, test cases, reproduction steps and contracts in `details` and the relevant authorized native handoff. Do not force all technical collaboration into a simplified summary or drop information another participant needs. Natural phrasing never means fabricated dialogue, greetings/thanks loops, acknowledgment-only posts, mandatory question rounds or more participants/messages.

For QA, explain the user-visible problem and distinguish checked/passed, failed, blocked and not yet checked. A test stopped at a preceding check did not verify its intended target. Measured layout constraints are not a visual inspection; disclose missing small-screen checks or final captures. Preserve unique case counts, retries, exact evidence and limits in `details`/validation records. These presentation rules change neither routing nor work scope, independence, required verification, file/Editor handoffs, authorization or honest completion. Raw HTML/Markdown image syntax is literal text; use structured `images` for attachments.

## Images during work and at completion

Keep visual reports infrequent. Do not post an image at every stage or just because one was produced. During work, attach an image only when the human explicitly asks, a visual choice needs their decision, or an error/reproduction or substantial visual change needs visual evidence that text alone cannot convey. Prefer one already available representative image; use a second only for a necessary comparison. Skip unchanged or nearly identical views. Do not generate or capture an extra image solely to fill a progress report. This does not reduce required implementation or QA validation: retain required evidence locally and post only what the recipient needs.

When that need exists, attach the already saved local image to your OWN substantive `room_post(kind="progress", messageKey="preview-stage-1", ..., images=[{path: ABSOLUTE_LOCAL_FILE, caption: SHORT_DESCRIPTION}])`. Briefly explain what changed, what is unfinished and the specific decision or problem shown. A progress post must not finish the job. Use a new messageKey for a new necessary visual report; reusing a key preserves the original snapshot even if the source file later changes or disappears.

The participant who creates an image or other visual deliverable (a screen, UI, design or 3D result) MUST personally attach one representative image of the ACTUAL final state to their OWN `room_reply(..., images=[...])`. Showing it only in native chat, mentioning a path, posting an intermediate preview or asking the director to repost it does not satisfy completion. Use the saved final output for generated images; reuse an accurate final-state image for other visual work, or capture that state once within the authorized workflow. Never present an old or intermediate view as the completed result. If the assignment omitted the image requirement, add it once with `room_claim(..., requireFinalImage=true)` before completion; dispatch:false forbids another assignment. The store rejects missing final attachments on required jobs and prevents director acceptance while such a creator job is unfinished. It validates attachment availability, not whether the pixels depict the true final state; that remains the creator's responsibility. If generation/capture/file access is blocked, report the concrete limitation with room_post(kind="blocker") and room_fail instead of claiming successful completion. Keep that blocker until an explicit authorized recovery. Text-only work needs no decorative image; intermediate reports remain infrequent.

The director includes this completion criterion in the next necessary assignment and checks the creator's saved attachment during normal integration. Do not wake staff just for an image reminder, scan other chats, add a collector/summary agent, or duplicate an already visible creator image in the director's final report. Reference the creator's completed result briefly; if the director creates their own visual output, the same personal-attachment rule applies.

Each message accepts up to 4 PNG/JPEG/GIF/WebP files, 8 MiB each. Paths must be absolute and readable by the meeting server on its host. Other machines' paths and remote URLs are not local attachments; do not claim a preview is published unless the tool succeeds. Never pass base64 in message text. Raw Markdown images/HTML remain literal text; the structured images field is the supported attachment route. Native chat images are not mirrored automatically. Do not scan old chats or folders, post another person's visuals as them, take duplicate captures, add periodic screenshots, or start extra AI turns merely for previews. Existing authorization for generation, paid work and screen capture still applies.

## Persistent role ownership

At task start, use the selected project's AGENTS.md and collaboration document for the human-approved responsibilities. Do not rely on chat memory alone. The director includes role, file ownership and validation ownership in the next necessary assignment; participants check those instructions before work. Keep configured names/routing unchanged. Apply these defaults only to roles already connected, and honor the human's project-specific overrides:

- Director: overall design, planning approval, prioritization, assignment, conflict resolution, integration and final acceptance.
- Planner: game systems, balance and level design; specify rules, numerical rationale, progression and acceptance criteria.
- Designer: character, UI, background and 3D asset planning/production; use the [design workflow](references/design-collaboration.md) for specifications, candidate review, revisions and developer handoff.
- Programmer: implementation, defect fixes, compilation/static checks and lightweight developer self-checks; hand off changed files, reproduction steps and evidence to QA.
- QA: test-case design, error reproduction, actual UI/behavior and regression validation; report expected/actual results, evidence and pass/fail/unverified scope.
- Sound: sound direction, asset specifications/selection and playback conditions.

Developer self-checks do not replace independent QA. After implementation, hand the shared application/Unity Editor operator role to QA for one consolidated change-relevant batch. Only one operator and one editor per file at a time. QA returns reproducible defects to the implementer, then retests only failed/newly affected cases; the director reviews and integrates. Do not repeat passing tests merely to change the operator. If QA is unavailable or lacks access, explicitly assign a substitute and disclose the independence/coverage limit. Do not silently label programmer-only checks as QA acceptance. Persist revised project responsibilities in project instructions; do not wake all participants merely to announce or confirm memory, and do not add recurring reminders.

## Collaboration efficiency

- The director owns overall design, planning approval within the human's scope, prioritization, assignment, conflict resolution and result integration. Assign implementation/design/QA to the existing relevant participants, with one editor per file. Policy/documentation decisions belong to the director. Do not wake everyone just to announce these rules; include them in the next necessary assignment.
- For routine work, aim for 1–2 substantive question/answer rounds per issue, not a mandatory meeting quota. A complete assignment needs no extra discussion. Only conflicting decisions, failed validation, missing essential information or new blocking evidence justify more rounds; state the reason and unresolved decision concisely. Never close an unresolved issue just to meet the limit.
- Handoffs contain only the original task/scope and constraints needed for execution, decisions, unresolved issues, changed files (including ownership), and relevant validation results/limits. Send a delta when updating a prior handoff. Link exact evidence instead of copying whole conversations, logs or repositories; retrieve only the necessary excerpt. Never compress away authorization boundaries or unresolved failures. Each participant still posts their own meaningful collaboration.
- After dispatch, follow [event waiting and minimal reads](references/event-waiting.md). Batch active targets with their cursors into one native wait, drop completed targets and act only on completion/failure/blocking decisions or human changes. Prefer the supported host default when current responsiveness/execution limits allow; do not impose a universal 60-second cap or a zero-timeout loop. Unchanged timeouts need no status/history reads, progress messages or analysis. Ordinary room progress must not also wake the director natively; consume native completion once without another notification. Retain active orchestration unless a verified authorized host mechanism covers both completion AND unexpected interruption after it yields. A participant's completion callback alone does not cover its own crash. No new watcher, heartbeat, cron, runtime or promise of zero usage.
- Review the changed diff and directly affected callers, data contracts, tests and required project instructions first. Expand only for a concrete dependency/risk, shared-interface change, failure or unexplained behavior; record why. Use one consolidated relevant validation batch after implementation, then rerun only failed or newly affected cases. Documentation-only work needs no application/Unity run.
- Use local deterministic tools for diffs, file checks, syntax/lint and tests (for this repository: git diff --name-only, git diff --check, node --check, the relevant node --test files, and scripts/check-layout.mjs for layout changes). Use npm test when store/bridge changes require it. Keep logs local and hand off only scope/pass/fail counts, failures and evidence paths. An unchanged result does not trigger AI or a meeting. AI handles interpretation, conflicts, unexpected failures and approvals. Do not add a background watcher or service just to enforce this policy. Do not claim a measured savings percentage without measurements.

## Peer questions

Use only the SAME project's configured member and host. Post a real question with kind=question, toMemberId and stable messageKey. created:true permits one necessary native send containing [TEAM-ROOM-PEER projectId requestId messageId], actual question and authorized context. Posting does not prove delivery. Never retry uncertain native delivery automatically.

The recipient checks the referenced question if needed and posts their OWN answer using replyTo, toMemberId=question.authorId, kind=answer and stable key. A peer-only responder without an assigned job uses room_post, not room_reply. Send the substantive answer back natively only when it unblocks work; no “answer posted” notifications. Unanswered questions keep the request open.

## Boundaries and idle

Every request operation requires projectId. Unknown project IDs, foreign members, cross-request answer links, duplicate/changed posts and unresolved completion are rejected. Names/roles/thread IDs come from selected configuration, never from the old six-role list. Configuration and source IDs are not independent caller authentication.

UI polls saved state while visible without invoking AI and stops while hidden. No AI heartbeat or idle monitoring. Storage/tool selection during an active model turn still has overhead; do not claim zero overall usage or measured savings. Pause is project-local and affects new work, not active turns. Preserve each project's own file ownership, one shared editor operator, save/data protections and build/upload/paid-work/paused-goal boundaries. A room connection does not grant those actions.
