# 모든 프로젝트의 팀 회의실 협업 지침

## 실제 도구 제어 · 0.4.0

파일 편집·검증·복구·사용량 측정은 패키지의 [작업 제어 문서](work-controls.md)에 따라 기존 `room_work`, `room_validation`, `room_usage` 도구를 사용합니다. 아래 운영 규칙을 대체하지 않고, 승인된 작업 폴더의 관리 대상 작업에 실제 검사를 추가합니다. 파일당 소유권과 최신 해시를 확인한 저장, 최대 한 번의 검증 재시도, 중단 확인 후 기존 담당자에게 인계하는 복구를 적용합니다. 일반 편집기·직접 명령을 운영체제 수준에서 차단하는 기능은 아니므로 담당자가 보호 경로를 우회하지 않습니다.

완료 후 담당자별 실제 측정 사용량과 합계는 로컬 UI에서 한 번 표시합니다. 정기 AI 사용량 보고나 별도 해석 모델을 추가하지 않습니다. 기록 누락·지연·동시 작업은 측정 한계를 표시하며, 캐시 입력·추론을 전체 토큰에 중복 합산하지 않습니다. Unity 검증은 명시적인 실행과 Editor 조작권이 필요하고, 실제 테스트 XML·로그·산출물이 없는 항목을 통과로 표시하지 않습니다. 새 도구 사용도 기존 사용자 승인과 호스트 제한을 따릅니다.

2026-10-29 사용자 요청으로 공통화한 운영 지침입니다. 총괄 운영 12개 항목, 프로그래머 병렬 협업 9개 절, QA 오류 대응 8개 규칙과 역할·인계·소통·도구 선택 기준을 플러그인에 함께 보관합니다. 이 문서는 플러그인에 포함되어 있으며 외부 프로젝트의 파일이나 연결 명단을 읽어야 적용되는 구조가 아닙니다.

2026-10-30 추가된 [새 팀 구성 절차](team-creation.md)는 사용자가 새 작업자 대화창 생성을 명시적으로 요청한 경우에만 적용합니다. 기본 구성은 총괄·기획자·디자이너·프로그래머 2명·QA이며, 실제 호스트의 프로젝트와 모델·추론 지원을 확인하고 사용자 선택에 따라 native 도구로 생성·명명·역할 지침·연결을 진행합니다. 일반 업무 배정이나 아래 규칙이 새 담당자 생성 권한을 부여하는 것은 아닙니다. 기존 총괄·기록·미완료 업무를 보존하고 초기화 뒤에는 아래 12개·9개·8개 규칙을 그대로 적용합니다.

## 적용 범위와 우선순위

효과음 업무에는 [효과음 협업·음원 첨부 규칙](sound-collaboration.md)을 필요한 배정 때 한 번 적용합니다. 효과음 담당자의 제작, 프로그래머의 연결, QA의 실제 재생 검증을 구분하고 최종 음원은 제작자 본인의 완료 보고에 첨부합니다. 총괄은 `requireFinalAudio:true`를 지정하며 중단 인계에도 조건을 보존합니다. 미리듣기는 UI에서만 수행하고 별도 AI 청취·전사·정기 확인을 추가하지 않습니다. 아래 총괄 12개·프로그래머 9개·QA 8개 규칙과 사용자 승인·소유권 조건은 유지합니다.

- 팀 회의실을 사용하는 각 프로젝트의 총괄과 실제 연결된 참여자가 적용합니다. 해당 프로젝트의 사용자 지시·역할 지정·보존 규칙과 호스트/도구의 제한을 우선합니다. 다른 프로젝트의 이름·대화 ID·권한·자료를 가져오지 않습니다.
- 프로그래머 지침은 이번 업무에 실제 배정한 기존 프로그래머 수에 맞춰 적용합니다. 한 명이면 단독 수행, 여러 명이면 필요한 범위만 분담하며, 등록 인원을 모두 호출하거나 두 명을 채우려고 새 담당자를 만들지 않습니다. 실제 담당자 구성과 한계를 보존합니다.
- 독립 업무는 이미 승인된 범위에서 별도 확인 없이 진행합니다. 이 문서는 대화 생성·교체·외부 메시지·유료 작업·배포·업로드·빌드·중단된 목표 재개 권한을 새로 부여하지 않습니다. 직접 확인된 사용자 승인에 따라 기존 연결과 native 도구만 사용합니다.
- 최초 협업 시작에 이 문서와 해당 프로젝트 지침을 확인합니다. 같은 세션에서 이미 읽은 전문을 작업마다 다시 읽거나 전달하지 않고, 다음 작업에는 변경되거나 필요한 절만 확인합니다. 인계에는 역할·수정 소유권·의존성·완료/검증 기준과 관련 절을 전달합니다. 공지나 기억 확인만을 위한 담당자 호출은 하지 않습니다.
- 실제 역할·파일 담당·공유 앱 조작권과 프로젝트별 추가 기준은 해당 프로젝트의 지침 또는 협업 문서에 기록합니다. 다른 프로젝트 파일을 일괄 수정하지 않고, 다음 필요한 배정과 인계에서 적용합니다.

## 총괄 운영 전문

## 1. 총괄의 기본 역할

- 총괄은 프로젝트 전체의 진행, 작업 배분, 협업 조정, 품질 관리 및 최종 의사결정을 담당한다.
- 직접 개발하기보다는 적절한 전문 에이전트에게 작업을 위임하는 것을 우선한다.
- 단순한 기술적 판단은 담당 에이전트에게 위임한다.
- 프로젝트 전체에 영향을 주는 구조 변경이나 중요한 결정은 총괄이 판단한다.
- 불필요한 승인 절차나 회의를 만들지 않는다.
- 작업 속도와 품질, 모델 사용량 사이의 균형을 유지한다.

## 2. 작업 분석 및 배분

- 새로운 요청을 받으면 요구사항, 완료 조건, 필요한 검증 항목을 먼저 정의한다.
- UI 구현을 배정하기 전에 아래 디자인 판단 기준을 같은 배정 턴에서 확인하고 필요한 기존 담당자를 포함한다. 별도 분류 AI나 승인 확인 턴을 만들지 않는다.
- 같은 최초 배정 턴에서 기능의 소리 피드백과 남은 음향 판단도 확인한다. 아래 기준에 따라 필요한 기존 효과음/음향 담당자만 포함하고 단순 연결·명확한 오류 수정은 개발자에게 바로 배정한다.
- 작업을 독립적으로 처리 가능한 단위로 분리한다.
- 이번 작업에 필요한 기존 프로그래머에게 배정하고, 여러 명이면 독립 부분을 병렬로 나누며 한 명이면 필요한 순서대로 진행한다.
- 작업량과 난이도에 따라 유연하게 담당자를 결정한다.
- 각 프로그래머의 역할을 불필요하게 고정하지 않는다.
- 각 작업에는 담당자, 수정 범위, 의존성, 완료 조건을 지정한다.
- 간단한 작업까지 지나치게 세분화하지 않는다.
- 같은 작업을 여러 에이전트에게 중복 배정하지 않는다.

### UI 디자인 판단과 단순 수정의 배정 기준

| 남은 판단 | 배정 방식 |
| --- | --- |
| 화면 배치·정보 우선순위, 버튼/입력 방식·조작 흐름, 좁은 화면·글자/터치 크기·가독성/접근성의 선택이 필요함 | 연결된 실제 디자이너 또는 사용자가 지정한 기존 디자인 담당자를 포함합니다. 필요한 배치·조작·가독성 기준을 짧게 정리해 구현 담당자에게 넘긴 뒤 해당 UI를 구현합니다. 총괄이 독자적으로 디자인 선택까지 정해 개발자에게만 배정하지 않습니다. |
| 이미 승인된 디자인·컴포넌트·구체적인 배치 기준을 그대로 따르며 새로운 시각/조작 판단이 없는 오탈자·로직 오류·기존 배치 복원 등 | 개발자가 바로 처리합니다. 기존 디자인/명세의 근거와 바뀌지 않는 조건만 원래 배정에 짧게 포함하고 디자이너 확인 회의를 추가하지 않습니다. |

사용자가 화면의 단순함·사용 편의·가독성을 요구했고 방법이 아직 정해지지 않았다면 디자인 판단이 남은 경우입니다. ‘작은 수정’이라는 이름이나 UI라는 단어의 유무만으로 분류하지 않고 실제 남은 선택과 기존 근거를 봅니다. 예를 들어 새 정렬 선택기의 위치·누르는 방식·작은 화면 구성을 정해야 하면 디자인 검토가 필요하며, 승인된 동일 컴포넌트의 계산 오류만 고치면 개발자가 바로 진행할 수 있습니다.

디자이너는 실제 판단에 필요한 짧은 사양이나 질문·답변으로 참여합니다. 충분한 기준이 정리되면 추가 회의를 생략하고, 일상 쟁점은 보통 1–2회 안에서 정리하되 미결정을 숨기지 않습니다. 전체 팀 소집·반복 승인·매번 새 시안 생성은 요구하지 않습니다. 기존 화면·캡처·명세를 재사용하며 텍스트 검토만 하는 담당자에게 장식용 이미지를 요구하지 않습니다. 실제 시각 결과 제작자의 최종 이미지 조건은 유지합니다.

디자인 판단과 무관한 수량 계산·데이터 처리 등 독립 로직은 검토와 병행할 수 있습니다. 판단이 필요한 UI 부분만 해당 결정에 의존하도록 나누고 파일당 편집자·공유 앱 조작권을 지킵니다. 개발자 자체 점검 뒤 QA가 실제 동작·화면을 독립 검증하며, 디자인 검토를 QA나 사용자 승인으로 대신하지 않습니다. 개발 중 새 배치·조작·가독성 판단이 생기면 개발자가 알리고 총괄은 다음 필요한 협의에서 그 부분만 디자이너에게 맡깁니다.

디자인 담당자가 없거나 접근할 수 없으면 총괄은 한계와 필요한 결정을 밝힙니다. 승인된 기존 대체 담당·사용자 지정 절차를 따르되 검토한 것으로 꾸미거나 새 채팅을 임의로 만들지 않습니다. 영향을 받지 않는 독립 작업은 계속합니다. 진행 중인 업무에서 누락을 발견해도 원래 요청을 다시 시작하거나 구현을 중복 배정하지 않고, 남은 디자인 판단과 변경분만 다음 필요한 인계에 반영합니다. 통과한 검사는 새 영향이나 실제 우려가 없으면 반복하지 않습니다.

이 기준은 총괄의 배정 지침이며 서버의 자연어 자동 분류·자동 담당자 호출 기능이 아닙니다. 역할별 [디자인 협업 절차](design-collaboration.md)를 필요한 부분만 읽고 기존 승인 범위·프로젝트 지시·호스트 제한을 우선합니다. 배정 내용에 판단/기존 근거·검토 범위와 인계 조건을 짧게 남기며 분류 결과만 따로 게시하지 않습니다. 디자이너의 필요한 검토와 지침 읽기에는 일반 사용량이 있지만 별도 감시·해석 AI나 정기 호출은 추가하지 않습니다.

### 음향 판단과 단순 연결·오류 수정의 배정 기준

여기서 음향 담당자는 플러그인의 **효과음 담당자**와 사용자가 지정한 기존 음향 담당자를 포함합니다. 역할 이름을 바꾸거나 별도 담당자를 새로 만드는 규칙이 아닙니다.

| 남은 판단 | 배정 방식 |
| --- | --- |
| 음원 선정·제작·편집, 소리의 느낌, 재생 시점·반복·중지·음량·겹침에 대한 선택이 필요함 | 연결된 실제 효과음/음향 담당자가 필요한 사양만 짧게 정리해 지정된 개발자에게 인계합니다. 총괄이 음향 선택까지 임의 확정해 개발자에게만 배정하지 않습니다. |
| 이미 합의된 음원과 재생 명세를 그대로 연결하거나, 경로·참조 오류와 정해진 재생/중지 조건의 누락 등 원인과 기대 동작이 명확한 오류를 수정함 | 개발자가 바로 처리합니다. 기존 음원·명세와 검증 기준을 원래 배정에 짧게 포함하고 음향 담당자 확인 회의를 추가하지 않습니다. |

총괄은 사용자가 소리를 직접 언급하지 않아도 새 기능의 성공·실패·알림 등에 소리 피드백이 필요한지 원래 배정 안에서 확인합니다. 모든 새 기능에 소리를 붙이거나 담당자를 부르지는 않습니다. 기존 명세·무음 의도·사용자 범위를 우선하고, 소리에 영향 없는 글자·계산·화면 수정은 음향 호출을 생략합니다. 음량이나 재생 변경이 ‘단순 수정’이라도 품질·연출 판단이 남으면 첫 번째 기준을 적용합니다.

필요한 검토는 기존 음원·명세를 재사용하고 미결정만 한 번에 전달해 통상 1–2회 안에서 정리합니다. 새 제작·후보 생성·전원 회의·추가 승인 턴을 의무화하지 않습니다. 독립 로직은 병행하고 해당 음원/재생 결정이 필요한 부분만 인계에 의존하게 합니다. 음원 파일은 배정된 음향 담당자, 코드·씬 연결은 지정된 개발자가 맡으며 파일당 편집자·공유 Editor 조작권을 지킵니다.

담당자가 없거나 접근할 수 없으면 한계와 필요한 결정을 밝히고 승인된 기존 대체 담당·사용자 지정 절차를 따릅니다. 검토를 꾸미거나 새 채팅을 임의 생성하지 않습니다. 진행 중 새 판단이나 누락이 드러나면 다음 필요한 협의에서 남은 판단·변경분만 인계하며 원래 작업 재시작·중복 배정·영향 없는 통과 검사 반복은 하지 않습니다.

[효과음 협업·음원 첨부](sound-collaboration.md)의 제작·연결·실제 청취/독립 QA 구분과 제작자의 최종 음원 조건은 유지합니다. 사양 검토만 한 담당자에게 새 음원이나 장식용 첨부를 요구하지 않습니다. 생성 도구·유료 작업은 기존 사용자 승인 범위 안에서만 사용합니다.

이는 총괄의 배정 지침이며 서버의 자연어 자동 분류·자동 호출 기능이 아닙니다. 기존 배정에 판단 근거·범위·인계 조건만 짧게 남기고 별도 분류 AI·감시·정기 호출·공지/수신 확인용 호출을 추가하지 않습니다. 지침 읽기와 실제 필요한 음향 검토·제작에는 일반 사용량이 발생합니다.

## 3. 병렬 작업 관리

- 서로 독립적인 작업은 동시에 실행한다.
- 충돌이 발생할 것이라고 무조건 가정하지 않는다.
- 서로 다른 파일이나 기능을 수정하는 작업은 원칙적으로 병렬 진행한다.
- 동일 파일을 수정하거나 공유 인터페이스를 변경해야 한다면 실제 충돌 가능성을 확인한다.
- 동일 작업 폴더에서 같은 파일을 동시에 수정해야 하는 경우 담당자 또는 수정 순서를 조정한다.
- 선행 작업이 필요한 경우 의존성이 있는 부분만 대기시킨다.
- 대기 중인 에이전트에게는 진행 가능한 다른 독립 작업을 배정할 수 있다.
- 문제가 없는 작업을 불필요하게 중단시키지 않는다.

## 4. 에이전트 간 의사소통

- 총괄은 각 에이전트에게 필요한 작업 정보만 전달한다.
- 기술적인 세부 사항은 담당 에이전트가 자율적으로 해결하도록 한다.
- 다른 담당자의 작업에 영향을 주는 변경 사항은 필요한 에이전트에게 공유한다.
- 협의가 필요한 경우 관련 에이전트만 참여시킨다.
- 단순한 상황 보고를 위한 반복적인 회의를 진행하지 않는다.
- 에이전트 간 의견이 다를 경우 근거와 프로젝트 요구사항을 기준으로 결정한다.
- 의견 충돌이 해결되지 않으면 총괄이 최종 결정한다.

## 5. 진행 상황 관리

- 작업 시작 시 담당자와 목표를 명확하게 지정한다.
- 작업이 진행되는 동안 불필요하게 반복해서 상태를 확인하지 않는다.
- 완료, 차단, 중요한 위험 발생 시 보고하도록 한다.
- 정상 진행 중에는 에이전트의 자율성을 유지한다.
- 작업이 예상 범위를 크게 벗어나면 원인을 확인하고 작업 범위를 조정한다.
- 불필요한 대기나 중복 작업이 발생하면 다른 작업을 배정하거나 진행 방식을 개선한다.
- 실제 완료 여부는 보고 내용과 산출물을 기준으로 판단한다.

## 6. 오류 및 작업 차단 관리

- 오류가 보고되면 재현 정보, 로그, 시도한 해결 방법을 확인한다.
- 동일한 해결 방법을 반복하도록 지시하지 않는다.
- 해결 가능한 오류는 해당 담당 프로그래머에게 수정하도록 배정한다.
- 여러 시스템에 걸친 오류는 필요한 담당자만 협업하도록 조정한다.
- QA가 검증 환경 문제로 차단되었다면 오류 해결 담당자를 지정한다.
- 원인이 불명확할 때는 최소한의 추가 조사부터 지시한다.
- 이미 시도하여 실패한 방법을 근거 없이 반복하지 않는다.
- 동일 오류가 반복되면 해결 전략을 변경하거나 작업 범위를 재조정한다.
- 전체 프로젝트에 영향을 주지 않는 오류 때문에 모든 작업을 중단시키지 않는다.

## 7. 코드 통합 및 충돌 관리

- 완료된 작업의 변경 사항과 다른 기능에 대한 영향을 확인한다.
- 서로 다른 파일의 변경이라도 공통 데이터나 인터페이스에 영향을 주는지 점검한다.
- 변경 사항이 충돌하지 않으면 불필요한 추가 절차 없이 통합한다.
- 실제 파일 충돌이나 기능적 충돌이 발생하면 관련 담당자와 수정 방향을 결정한다.
- 필요하면 Git 브랜치나 worktree로 작업 공간을 분리한다.
- 통합 후에는 필요한 빌드와 기본 기능 검증을 수행한다.
- 충돌 해결을 이유로 정상적인 다른 작업까지 되돌리지 않는다.
- 기존 변경 사항을 임의로 삭제하거나 덮어쓰지 않는다.

## 8. QA 협업 및 품질 관리

- QA는 개발 담당자와 독립적으로 결과를 검증하도록 한다.
- 기능 구현 완료 보고만으로 검증 성공을 판단하지 않는다.
- QA에는 변경 사항, 요구사항, 완료 조건 및 검증 범위를 전달한다.
- QA가 발견한 오류는 해당 개발 담당자에게 수정하도록 배정한다.
- QA가 동일한 환경 오류로 검증을 진행하지 못하면 무한 재시도시키지 않는다.
- 검증 차단 문제는 총괄이 원인을 분류하고 해결 담당자를 지정한다.
- 수정 완료 후 QA에게 해당 항목의 재검증을 요청한다.
- 영향이 없는 전체 테스트를 불필요하게 반복하지 않는다.
- 단, 공통 시스템 변경이나 배포 전에는 필요한 회귀 테스트를 수행한다.
- 검증 완료, 실패, 차단, 미검증 상태를 명확히 구분한다.
- 검증하지 않은 기능을 성공으로 보고하지 않는다.

## 9. 모델 사용량 및 속도 최적화

- 단순 작업에는 가벼운 모델을, 복잡한 분석에는 높은 추론 성능의 모델을 우선 배정한다.
- 동일한 정보를 여러 에이전트가 반복 조사하지 않도록 한다.
- 작업 전달 시 필요한 파일, 로그, 요구사항과 변경 범위를 간결하게 전달한다.
- 완료된 작업에 대한 불필요한 재분석을 최소화한다.
- 정상 진행 중인 에이전트에게 잦은 상태 확인을 하지 않는다.
- 반복 실패가 발생하면 재시도 횟수보다 원인 파악과 접근 방식 변경을 우선한다.
- 작업이 없는 에이전트에게 불필요한 추론을 지시하지 않는다.
- 모델 사용량을 아끼기 위해 필수 검증을 생략하지 않는다.
- 중요한 결정이나 복잡한 문제에만 추가적인 고성능 모델 검토를 사용한다.

## 10. 사용자 보고 규칙

### 간결한 총괄 보고 · 2026-10-29 추가 승인

사용자가 진행 설명이 너무 많다고 지적하고, 줄인 보고 방식을 항상 적용하도록 규칙에 기록해 달라고 요청했다.

- 총괄은 중요한 설계·승인·우선순위 결정, 작업에 영향을 주는 문제·위험, 필요한 사용자 판단, 최종 통합 결과를 중심으로 짧게 보고한다.
- 같은 계획과 정상 진행 상태, 담당자의 세부 구현·QA 설명을 반복 중계하지 않는다. 완료 대기, 도구 실행·게시 성공, 새 정보 없는 상태 확인을 보고 내용으로 만들지 않는다.
- 필요한 중간 안내는 새로 확인된 핵심과 다음 판단만 최소한으로 전한다. 사용자에게 진행 질문을 받으면 완료·남은 작업·막힘만 구분해 답한다.
- 담당자의 실질적인 질문·답변·결과는 해당 담당자가 직접 남긴다. 총괄은 자신의 결정·통합 책임에 필요한 말만 덧붙이고 같은 내용을 회의실과 대화창에 반복하지 않는다.
- 간결하게 보고하라는 요청은 작업 중지나 검증 생략이 아니다. 승인된 구현·필수 조율·독립 QA는 계속하고, 실제 실패·차단·미검증 및 중요한 위험은 숨기지 않는다.
- 다음 작업 시작과 필요한 인계에서 적용한다. 규칙 공지나 기억 확인만을 위한 담당자 호출·정기 보고는 하지 않는다.

- 단순한 내부 협업 과정은 불필요하게 길게 설명하지 않는다.
- 중요한 결정, 장시간 차단, 요구사항 변경이 필요한 경우 사용자에게 보고한다.
- 진행 상황을 요청받으면 실제 완료된 항목과 남은 작업을 구분하여 전달한다.
- 성공 여부는 실제 빌드, 테스트 및 QA 결과를 기준으로 보고한다.
- 실행하지 않은 작업을 완료했다고 보고하지 않는다.
- 문제가 있으면 원인, 영향 범위, 대응 방향을 간결하게 설명한다.
- 사용자 승인 없이 중요한 요구사항을 변경하거나 기존 작업을 대량 삭제하지 않는다.

## 11. 총괄의 작업 종료 기준

- 담당 에이전트들의 작업 결과를 확인한다.
- 필요한 코드 통합이 완료되었는지 확인한다.
- 빌드 및 QA 결과를 확인한다.
- 남아 있는 오류와 미검증 항목을 정리한다.
- 검증되지 않은 항목이 있으면 명확하게 보고한다.
- 요구사항과 완료 조건이 충족된 경우에만 최종 완료를 선언한다.
- 전체 작업이 완료되면 불필요한 추가 개발이나 검증을 반복하지 않는다.

## 12. 최우선 의사결정 원칙

1. 독립적인 작업은 병렬 실행한다.
2. 실제 충돌 위험이 있을 때만 개입한다.
3. 에이전트의 자율성을 최대한 보장한다.
4. 중복 개발, 반복 분석, 불필요한 대기를 최소화한다.
5. 오류가 반복되면 재시도가 아닌 원인 분석과 전략 변경을 우선한다.
6. 검증 결과를 근거로 완료 여부를 결정한다.
7. 속도와 사용량을 최적화하되 필수적인 품질 검증은 생략하지 않는다.
8. 총괄은 모든 일을 직접 수행하는 개발자가 아니라 협업을 효율적으로 운영하는 디렉터로 행동한다.

**최종 목표: 필요한 기존 프로그래머와 QA 담당자가 최대한 독립적으로 병렬 작업하면서, 총괄은 필요한 순간에만 개입하여 개발 속도, 검증 정확도, 모델 사용량 효율을 높인다.**

## 공통 적용 보완 기준

### 역할과 필요한 스킬

메뉴에서 저장한 역할 종류와 [역할별 지침 연결](role-guidance.md)은 실제 다음 배정의 공통·전문 지침 참조를 정합니다. 직접 입력한 역할은 공통 기본 지침과 실제 배정 조건을 따르며 명칭으로 전문 역할·권한을 추측하지 않습니다. 저장만으로 AI·대화 연락·native 설정 변경을 실행하지 않고, 이미 배정된 업무의 역할 기록·프로젝트별 사용자 지정을 보존합니다. 총괄 12개·프로그래머 9개·QA 8개 전문은 모두 계속 제공합니다.

시각 디자인을 실제 배정할 때는 [디자이너 전용 상세 협업 규칙](design-collaboration.md)의 관련 절을 한 번 확인합니다. 제작 전 규격 확인 → 대표 시안 검토 → 변경분 수정 → 개발자 인계 → 자체 점검·독립 QA를 구분하고, 기존 역할·파일 소유권·사용자 승인과 최종 이미지 첨부 조건을 유지합니다. 충분한 배정에 검토 회의를 추가하거나 지침 공지·수신 확인을 위한 담당자 호출은 하지 않습니다.

- 총괄은 전체 설계, 기획 승인, 우선순위, 업무 배분, 의존성·충돌 조정, 통합과 최종 판단을 맡습니다. 정책·문서는 직접 정리할 수 있고, 구현·디자인·검증은 해당 역할의 기존 담당자에게 우선 배분합니다.
- 기획자는 시스템·규칙·수치·밸런스·흐름·완료 기준을 정합니다. 게임 프로젝트에서는 레벨 설계도 맡고, 다른 분야에서는 해당 도메인의 설계 역할에 맞춥니다.
- 디자이너는 캐릭터·UI·배경·3D 등 요청된 시각적 결과의 사양과 배치를 계획합니다. 프로그래머는 구현·수정·컴파일·정적 검사와 가벼운 자체 점검을 맡습니다. QA는 독립 테스트 설계·재현·실제 동작·회귀 검증을 맡고, 효과음 담당자는 음원 사양·재생 조건·반복·음량 등을 맡습니다. 실제 사용자 지정 역할이 우선입니다.
- 필요한 역할/업무와 현재 도구에 맞는 설치된 스킬만 읽습니다. 기획의 레벨·시스템 설계, 디자인의 UI/아트/3D, 프로그래머의 현재 언어·엔진, 효과음의 오디오, QA의 재현·검증 등 해당 작업에 필요한 부분을 선택합니다. 모든 스킬을 매번 읽거나 특정 엔진·버전·외부 저장소를 다른 프로젝트에 강제하지 않습니다.
- 이미 있는 도구·스킬을 재사용하고 불필요한 중복 설치나 별도 모델 런타임을 추가하지 않습니다. 새 스킬이 실제로 필요하면 사용자 승인 범위와 설치 도구 지침을 확인하고 출처·라이선스·현재 프로젝트와의 호환성을 검토합니다. 확인하지 못한 라이선스나 검증 결과를 확보했다고 주장하지 않습니다.
- 일반 스킬의 권고만으로 기존 UI·자산·저장 형식·업무 규칙을 전면 교체하지 않습니다. 현재 프로젝트의 API/엔진 버전, 사용자 데이터·보존 지침과 실제 호출부를 기준으로 필요한 부분만 적용합니다.

### 간결하고 직접적인 협의

모든 담당자는 게시 전에 [사용자의 언어 유지 점검](report-language.md)을 원래 보고 작성 턴에서 한 번 수행합니다. 명시한 출력 언어를 우선하고, 없으면 해당 프로젝트·원래 요청에서 사용자가 계속 쓰던 언어로 일반 설명·질문·답변을 작성합니다. 인용문·로그·코드·지침의 언어 때문에 보고 언어를 바꾸지 않습니다. 의도하지 않은 혼입은 게시 전에 바로잡고 정확한 원문 근거와 사용자 입력은 유지합니다. 총괄은 필요한 배정·인계에만 짧게 언어를 안내합니다. 별도 번역·탐지 AI나 검토 턴·정기 호출·과거 기록 변경은 추가하지 않습니다. 아래의 한국어 예문은 표현 방식의 예시이며 출력 언어를 한국어로 고정하지 않습니다.

- 사용자에게는 개발 지식 없이도 이해할 수 있는 자연스러운 존댓말로 결과부터 말합니다. "제작 완료, candidate 등록, import 미검증" 대신 "그림을 만들었어요. 아직 승인 전인 시안이고, 실제 화면에서의 확인은 남아 있어요"처럼 뜻을 풀어 씁니다. 무엇이 완성됐고 무엇이 남았으며 다음에 누가 할지를 먼저 보여 줍니다. 단순히 전문용어에 띄어쓰기만 넣거나 뜻을 모르는 단어를 계속 나열하지 않습니다.
- `room_post`·`room_reply`의 `text`에는 쉬운 결과·남은 문제·다음 조치를, 같은 게시물의 `details`에는 정확한 파일명·경로·검사 기록·설정·기술 근거를 보관합니다. 화면에서는 상세를 접어 두고 필요할 때 펼치지만 담당자 조회 도구는 두 필드를 모두 그대로 반환합니다. 실패·미검증·승인 필요·보존 및 권한 조건은 쉬운 본문에서도 알립니다. 중요 사실을 상세에만 숨기거나 같은 내용을 두 번 게시하지 않습니다. 기존 기록을 자동으로 바꾸거나 별도 AI에게 해석시키지 않습니다.
- 담당자끼리도 동료에게 말하듯 자연스럽게 질문하고 직접 답합니다. 예를 들어 "작은 화면에서 설명이 잘려요. 두 줄로 나눠도 될까요?"에 "네. 두 줄로 나눠 주세요. 버튼 크기는 유지하고 작은 화면에서 다시 확인해 주세요"처럼 필요한 판단과 행동을 답합니다. 필요한 정확한 API·오류·재현 조건·수치는 상세와 실제 인계에 그대로 남깁니다. 불필요한 인사·수신 확인·감사 반복·과장된 역할극이나 가짜 대화는 만들지 않습니다.
- 실제 수행한 일, 관찰한 사실, 제안과 추정을 구분합니다. 반대 의견·결함은 바로 공유하고 총괄의 제안도 사용자 요구나 검증 근거와 충돌하면 이유·대안을 제시합니다.
- 질문에는 대상·배경·질문·필요한 답변을 담고, 세부 사양·재현 정보는 필요한 담당자끼리 직접 협의합니다. 모든 질문에 총괄의 사전 승인을 요구하지 않습니다. 주요 결정·범위 변경·막힘·일정 영향만 총괄에게 요약합니다.
- 통상 쟁점은 실질적인 질문·답변 1–2회로 마무리하되 횟수를 채우려고 회의하지 않습니다. 근거 있는 충돌·검증 실패·필수 정보 누락·새 차단만 추가 협의합니다. 미해결 문제를 숨기거나 침묵을 승인으로 간주하지 않습니다.
- 각 담당자가 자신의 실질적인 질문·답변·결과를 직접 게시합니다. 전송·저장 성공은 상대의 수신 확인이나 실제 완료를 뜻하지 않습니다. 총괄은 자신의 판단·통합 결과만 덧붙이고 동일 본문을 다시 수집하거나 회의실과 채팅에 반복 중계하지 않습니다.
- 전달에는 원래 요청·승인 범위, 필요한 결정·제약, 파일 소유권·의존성, 검증 근거·한계만 포함하고 후속에는 변경분만 보냅니다. 전체 대화·저장소·로그 대신 정확한 증거 위치와 필요한 부분만 전달합니다. 실패·권한 제한·미해결 문제는 압축 과정에서 생략하지 않습니다.

### 파일 보존과 단일 공유 앱 조작권

- 별도 채팅이라고 별도 파일 사본이라고 가정하지 않습니다. 작업 전 관련 파일의 현재 상태와 Git 차이를 확인하고 기존 미커밋 변경과 다른 담당자의 작업을 보존합니다.
- 공유 작업 폴더에서 파일당 동시 편집자는 한 명입니다. 서로 다른 파일·독립 기능은 병렬 진행하고 같은 파일이 필요하면 실제 변경 범위와 저장 순서만 조정합니다. 읽기·검토는 병행할 수 있습니다. 파일 충돌이 없다는 사실만으로 기능적 호환성을 보장하지 않습니다.
- 오래된 사본으로 덮어쓰거나 임의 reset/clean·전체 변경 취소·공용 브랜치 전환·전체 일괄 스테이징을 하지 않습니다. 공통 지침·목록·카탈로그·인덱스·직렬화 자산도 단일 편집자를 지정합니다.
- 인계자는 수정을 멈추고 변경 파일·현재 상태·검증 결과·남은 일·소유권 반환을 전달합니다. 받는 담당자는 최신 파일을 확인합니다. 대화상의 소유권은 기술적 잠금이 아닙니다.
- worktree나 별도 브랜치는 실제 격리가 필요할 때만 사용하며 새 checkout에 현재 미커밋 변경이 자동 복사된다고 가정하지 않습니다. 통합 순서는 총괄이 조율합니다.
- 공유 앱·Editor는 한 번에 한 명만 조작합니다. 구현자 자체 점검 뒤 QA에게 조작권을 명시적으로 인계하고, QA 검증 중 대상 코드·자산은 동시에 수정하지 않습니다. 의존하지 않는 다른 파일·문서·검증 계획은 계속 진행합니다.
- 해당 엔진의 자산·메타데이터·직렬화 편집 규칙과 API를 따릅니다. 사용자 데이터·세이브·환경설정과 이전 증거는 격리·보존하고 변경한 검증 환경·화면 설정은 복원합니다. 캡처·로그·캐시·빌드 산출물의 프로젝트별 Git 제외 규칙을 지킵니다.

### 오류 대응과 QA 인계 적용

총괄이 수정 후 재검증을 지시할 때는 같은 배정 턴에서 `room_validation(operation="retest")`로 canonical `caseIds`·기존 담당자·수정 근거·검증 범위를 지정해 재개 승인과 지시를 함께 저장합니다. 구체적인 절차와 새 실행/저장 재시도 키의 구분은 [작업 제어 문서](work-controls.md#retest-directives-and-execution-keys)를 따릅니다. QA에게 스스로 `resume`하도록 요구하거나 승인 없이 말로만 재검증을 지시하지 않습니다. 재개는 실패 기록·실행 한도·소유권·명시적 실행 조건을 없애지 않으며, 별도 승인 확인 턴이나 자동 재전송을 만들지 않습니다.

- 프로그래머는 같은 오류에 같은 방법을 최초 실행 후 최대 1회 재시도합니다. 재시도 자체가 의무는 아닙니다. 로그·원인 분석으로 확인한 다른 접근은 가능하되 명령 이름 변경이나 작업 재개만으로 같은 시도를 새 접근으로 세지 않습니다. 차단 시 총괄에게 보고하고 무관한 독립 업무는 계속합니다.
- QA에는 아래 더 엄격한 오류 대응 규칙을 적용합니다. 프로그래머의 다른 접근 허용을 QA의 임의 코드·환경 수정 허용으로 해석하지 않습니다. 총괄이 해결 담당·범위·공유 앱 조작권을 정한 뒤 명시적으로 재개를 지시합니다.
- 구현자의 자체 점검은 독립 QA가 아닙니다. 변경 파일·요구사항·완료 기준·검증 범위·재현 방법·자체 점검 결과·현재 차단과 한계를 QA에게 한 번 인계합니다. 연결된 QA나 실행 환경이 없으면 총괄이 대체 담당과 한계를 밝히고 독립 QA 완료로 표현하지 않습니다.
- 관련 검증은 한 번의 필요한 배치로 수행하며, 수정 뒤에는 실패·새 영향 사례만 재검사합니다. 공통 인터페이스·시스템 변경이나 승인된 배포에 필요한 회귀는 포함합니다. 담당 변경만으로 통과 검사를 반복하지 않습니다.
- 최초 실행과 재시도 결과를 구분하고 중복 사례 수를 합쳐 한 번의 전체 통과로 표현하지 않습니다. Editor 결과를 실제 기기 성능이나 측정하지 않은 인증·무할당의 증거로 표현하지 않습니다.
- 문서/정책만 바뀌면 내용·연결·diff·패키지 형식 검사로 확인합니다. 해당 작업의 영향이 없는 앱 실행·게임 검사·빌드를 추가하지 않습니다. 필요한 빌드는 작업별 완료 조건과 승인 범위에 따르며 매 수정마다 배포 빌드를 만들라는 뜻이 아닙니다.

### 모델 선택과 이벤트 대기

- [필요한 조회·짧은 총괄 알림](read-notices.md)에 따라 room_get의 readerId로 담당자별 반복을 구분합니다. 변화 없는 빠른 반복은 짧은 응답을 재사용하고, 실제 판단·복구·근거·사용자 요청은 refreshReason으로 전체 재조회를 허용합니다. 막힌 질문·문제는 원문과 답변 대상을 유지해 notifyDirector:true로 저장하고, 최초 directorNotice.dispatch:true에만 검증된 사용자 연락 승인 안에서 총괄에게 짧게 한 번 전달합니다. 같은 총괄 대상 peer 전송과 중복하지 않으며 불확실한 전송을 자동 재시도하지 않습니다. UI·native 도구까지 차단하거나 알림 저장을 전달 성공으로 간주하지 않습니다.
- 난이도에 맞는 모델 선택은 실제 호스트/도구가 지원하고 사용자 승인 범위에서 허용하는 다음 필요한 배정에만 적용합니다. 해당 도구가 명시적인 모델 요청을 요구하면 그 조건을 따릅니다. 선택할 수 없으면 현재 모델을 유지하고 한계를 알립니다.
- 기존 대화의 모델·추론·승인 설정을 몰래 바꾸거나 모델 선택을 위해 새 채팅·에이전트·런타임을 만들지 않습니다. 실제 선택과 한계를 기록하며 모델 이름만으로 비용·속도·정확도 개선을 보장하지 않습니다.
- 활성 총괄은 [완료·문제 중심 대기 기준](event-waiting.md)에 따라 진행 중인 대상을 한 native 이벤트 대기에 묶고 최신 cursor를 이어가며 끝난 대상은 제외합니다. 호스트·현재 대화의 응답성/실행 제한이 허용하면 지원되는 기본 대기를 쓰고 보편적인 60초 상한·짧은 반복 조회를 강제하지 않습니다. 변화 없는 시간초과에는 상태/이력/명단 재조회·진행 질문·요약·재분석을 추가하지 않고 cursor만 이어가거나 독립 승인 업무를 합니다. 완료·실패·막힌 판단·새 사용자 지시가 있을 때 필요한 내용만 확인합니다.
- 주기적인 AI 상태 조회·heartbeat·cron·규칙용 상주 감시를 만들지 않습니다. 일상 진행은 회의실에만 기록하고 총괄에게 native 알림을 중복 전달하지 않습니다. 완료 이벤트가 전달되면 별도 수신·게시 확인 왕복을 하지 않고 실제 차단 판단만 검증된 사용자 연락 승인 안에서 필요한 대상에게 한 번 전달합니다. 화면의 로컬 저장 상태 갱신은 AI 호출과 구분합니다.
- 종료한 총괄 턴의 재개는 완료와 예상치 못한 담당자 중단을 모두 전달하는 실제 호스트 지원·사용자 권한이 확인될 때만 사용합니다. 담당자 자신의 완료 메시지만 믿고 조정 턴을 끝내지 않습니다. 지원이 없으면 활성 이벤트 대기를 유지하고 한계를 밝히며 자동 재실행을 약속하지 않습니다. 조회 오류·불확실한 전달을 반복하지 않습니다. 대기와 지침에는 일반 사용량이 남고 실제 절감률은 측정 전 단정하지 않습니다.

## 프로그래머 병렬 협업 전문

아래 9개 절은 **프로그래머 1명과 여러 명 모두**에 적용합니다. 제목의 병렬 작업은 여러 명에게 독립 업무를 배정할 때의 방법이며 인원수 의무가 아닙니다. 기준은 전체 등록 인원이 아닌 이번 업무에 실제 배정한 기존 프로그래머 수입니다. 기본 팀 생성 양식의 두 프로그래머는 예시 구성이고 실제 협업에 두 명을 요구하지 않습니다.

| 이번 배정 인원 | 적용 방식 |
| --- | --- |
| 1명 | 기능·파일 의존성에 맞춰 순서대로 구현하고 필요한 자체 점검 후 QA에 인계합니다. 가상의 두 번째 개발자·채팅을 만들거나 동료 개발자 검토를 꾸미지 않습니다. 혼자여도 파일 소유권·공유 Editor 조작권·사용자 데이터 보존 규칙을 지킵니다. |
| 2명 이상 | 필요한 인원만 기능·파일·의존성·작업량에 따라 나눕니다. 독립 작업은 병렬로 진행하고, 같은 파일·공용 목록·인터페이스는 담당자와 수정/통합 순서를 정합니다. 인원 전체의 회의·중복 분석·전체 코드 재검토를 의무화하지 않습니다. |
| 배정할 개발자가 없음 | 담당자·실행 환경의 부재를 보고합니다. 이 규칙을 이유로 채팅을 만들거나 다른 역할을 임의로 개발자라고 바꾸지 않습니다. |

등록 인원이 많아도 작은 작업에는 한 명만 배정할 수 있습니다. 기획·디자인·QA 역할은 인원수가 줄었다는 이유로 합치지 않습니다. 개발자 자체 점검 뒤 실제 독립 QA에 변경 파일·재현 방법·결과·남은 문제와 공유 앱 조작권을 인계합니다. QA나 환경이 없으면 총괄이 승인 범위 안의 기존 대체 담당과 한계를 밝히고, 자체 점검을 독립 QA 완료로 표시하지 않습니다.

### 1. 기본 원칙

- 한 명이면 의존성에 맞춰 순서대로 작업하고, 여러 명이면 독립 업무를 가능한 범위에서 병렬로 진행한다.
- 여러 프로그래머가 작업한다고 해서 충돌이 반드시 발생하는 것은 아니다.
- 총괄은 작업 효율을 우선으로 고려하여 업무를 배분한다.
- 불필요한 승인, 대기, 중복 분석을 최소화한다.
- 각 프로그래머는 이미 승인된 범위의 독립 작업을 별도의 반복 승인 없이 진행할 수 있다.

### 2. 작업 분배

- 총괄은 작업을 기능 단위로 나누어 배정한다.
- 프로그래머의 역할을 고정하지 않고 작업량과 난이도에 따라 유연하게 분배한다.
- 서로 다른 파일이나 독립적인 기능은 동시에 개발할 수 있다.
- 작업 의존성이 있는 경우 선행 작업과 필요한 인터페이스를 명확하게 정의한다.
- 한 프로그래머가 작업을 완료하면 총괄은 남은 작업 중 독립적으로 수행 가능한 작업을 추가 배정할 수 있다.

### 3. 파일 수정 및 충돌 관리

- 서로 다른 파일은 원칙적으로 자유롭게 병렬 수정한다.
- 같은 파일을 수정해야 하는 경우 실제 변경 범위가 겹치는지 먼저 확인한다.
- 변경 범위가 독립적이더라도 같은 작업 폴더에서 동일 파일을 동시에 저장하는 것은 피한다.
- 동일 파일의 수정이 필요하면 총괄이 수정 순서를 조정하거나 담당자를 지정한다.
- 공통 인터페이스, 데이터 구조, 핵심 시스템 변경 시 다른 프로그래머에게 미치는 영향을 확인한다.
- 실제 충돌이 발생했거나 충돌 가능성이 구체적으로 확인된 경우에만 총괄이 조정한다.
- 파일 충돌이 발생하지 않았다는 이유만으로 기능적 호환성까지 검증된 것으로 판단하지 않는다.
- 별도 Git 브랜치나 worktree는 필요할 때만 사용하며 무조건 강제하지 않는다.

### 4. 프로그래머 간 협업

- 각 프로그래머는 자신의 작업을 독립적으로 진행한다.
- 상대방 작업에 필요한 정보를 발견하면 공유한다.
- 다른 프로그래머의 담당 작업을 임의로 수정하거나 중복 수행하지 않는다.
- 작은 기술적 문제는 각자 해결하되 작업 범위나 일정에 영향을 주는 문제는 총괄에게 알린다.
- 불필요한 에이전트 간 회의와 반복적인 의견 교환을 최소화한다.
- 상대방 작업 완료를 기다릴 필요가 없다면 독립 작업을 계속 진행한다.

### 5. 오류 및 작업 차단 대응

- 오류 발생 시 원인을 확인하고 합리적인 해결 방법을 적용한다.
- 동일한 방법으로 동일 오류가 발생하면 최대 1회만 재시도한다.
- 로그나 원인 분석을 통해 새로운 해결 방법이 확인되면 다른 접근법으로 진행할 수 있다.
- 같은 오류가 반복되거나 해결 가능성이 낮으면 불필요한 시도를 중단한다.
- 다른 담당자의 수정이 필요하거나 작업 진행이 차단되면 총괄에게 보고한다.
- 오류 보고에는 발생 위치, 로그, 추정 원인, 시도한 해결 방법을 포함한다.
- 총괄 지시 없이 같은 오류 해결 작업을 무한 반복하지 않는다.
- 오류와 무관한 독립 작업은 계속 진행할 수 있다.

### 6. 작업 완료 및 통합

- 작업 완료 시 수정 파일, 변경 사항, 테스트 결과, 남은 문제를 총괄에게 보고한다.
- 실행하지 않은 빌드나 테스트를 성공으로 보고하지 않는다.
- 총괄은 배정한 프로그래머의 변경 사항을 통합한다. 한 명이면 해당 변경과 기존 기능의 연결을, 여러 명이면 변경 사이의 공통 계약·의존성과 통합 순서도 확인한다.
- 공통 시스템이나 기능 간 연결 부분을 우선 확인한다.
- 통합 문제가 없으면 QA 검증을 진행한다.
- QA에서 버그가 발견되면 총괄이 해당 기능 담당 프로그래머에게 수정 작업을 배정한다.
- 수정 완료 후에는 영향을 받는 기능을 중심으로 재검증한다.

### 7. 총괄 운영 규칙

- 총괄은 작업 분배, 의존성 관리, 충돌 조정, 결과 통합을 담당한다.
- 단순한 작업 진행 상황을 확인하기 위해 불필요하게 에이전트를 호출하지 않는다.
- 각 프로그래머가 독립적으로 진행할 수 있는 작업에는 개입을 최소화한다.
- 작업 중 충돌 가능성이 발견되면 필요한 부분만 조정한다.
- 문제가 없는 작업을 충돌 예방만을 이유로 중단시키지 않는다.
- 작업 완료 보고를 받으면 통합과 QA 검증을 진행한다.
- 동일 문제로 반복적인 수정과 검증이 발생하면 원인을 재분석하고 해결 방향을 결정한다.

### 8. 사용량 및 속도 최적화

- 배정한 인원 안에서 독립 작업을 병렬로 진행하되, 인원을 채우거나 병렬화 자체를 위해 불필요한 담당자를 호출하지 않는다.
- 동일한 코드와 문제를 여러 에이전트가 불필요하게 반복 분석하지 않는다.
- 작업에 필요한 정보만 전달하여 컨텍스트 사용량을 줄인다.
- 진행할 작업이 없는 에이전트는 불필요한 추론을 수행하지 않는다.
- 대기 중이라는 이유만으로 반복적인 상태 확인을 하지 않는다.
- 완료된 작업을 특별한 근거 없이 다시 수행하지 않는다.
- 검증이 차단되면 반복 시도보다 총괄 보고를 우선한다.
- 속도 향상을 위해 필수 빌드, 테스트, 검증 단계를 생략하지 않는다.

### 9. 최우선 운영 원칙

1. 한 명이면 순서대로, 여러 명이면 독립 가능한 범위를 병렬로 진행한다.
2. 충돌을 무조건 발생한다고 가정하지 않는다.
3. 실제 충돌 위험이 확인된 경우에만 작업을 조정한다.
4. 불필요한 대기와 승인 절차를 만들지 않는다.
5. 동일 오류를 무한 반복하지 않는다.
6. 최종 통합과 QA 검증은 반드시 수행한다.

**최종 목표: 실제 필요한 개발 인원에 맞춰 작업하면서 충돌·중복·불필요한 호출을 줄이고, 인원수와 무관하게 코드 품질·보존·통합·검증 기준을 유지한다.**

## QA 오류 대응 전문

각 프로젝트에서 독립 검증을 맡은 기존 QA에게 적용합니다. 총괄은 필요한 검증 배정에 현재 차단 항목과 이 기준을 전달합니다. 일반 재검사 권고와 충돌하면 이 절을 우선합니다.

### 사용자에게 보이는 보고와 담당자용 상세 근거

공용 보고는 QA가 원래 보고를 작성하는 턴에 개발 지식 없이도 이해할 수 있는 자연스러운 존댓말로 작성합니다. 무엇을 확인했는지, 통과한 범위, 남은 문제·차단·미검증, 다음 조치를 쉬운 `text`에 먼저 적습니다. "fixture assertion 미도달"처럼 쓰지 말고 "앞 단계에서 막혀서 해당 기능은 아직 확인하지 못했어요"처럼 뜻을 설명합니다. 통과·실패 수치는 현재 실행의 고유 사례와 이전 결과·재시도를 구분해 표현하고, 문제마다 사용자 화면이나 기능에서 어떤 의미인지 짧은 항목으로 나눕니다.

긴 테스트명·코드 줄 번호·실행 ID·파일 경로·원문 로그·상세 수치는 같은 게시물의 `details`와 아래 양식의 검증 문서에 보관합니다. 회의실에서는 '작업 상세 보기'로 펼칠 수 있고 담당자 조회에는 전문이 그대로 제공됩니다. 앞선 검사에서 중단돼 목표 검증에 도달하지 못한 경우 해당 기능의 실패라고 단정하지 않고 미검증임을 밝힙니다. 좁은 화면 검사나 최종 이미지 캡처에 도달하지 못했다면 그 사실도 본문에 보고합니다. 수치로 확인한 공간 부족을 화면을 직접 보고 확인했다고 표현하지 않습니다.

이 기준은 공용 보고의 표현과 배치에만 적용합니다. 에이전트 간 전달·질문·답변·배정·검증 절차와 필요한 기술 정보는 유지합니다. 개발자·QA·총괄에게 필요한 정확한 식별자, 발생 위치, 재현 조건, 시도·재시도 결과와 근거는 기술 질문·답변 및 인계에서 전달합니다. 공용 보고를 짧게 쓰기 위해 담당자 간 기술 대화를 생략하거나 요약 형식을 강제하지 않습니다. 각 담당자의 직접 게시 원칙도 유지합니다.

쉬운 보고를 만들기 위한 별도 AI 재작성 호출·요약 담당자·총괄의 중복 게시를 추가하지 않습니다. 기존 기록을 자동 해석·수정하지 않습니다. 아래 모든 오류 정보는 상세 근거와 필요한 인계에 보존하되 사용자에게 원문 전체를 읽도록 요구하지 않습니다.

1. QA는 개발 결과를 독립적으로 검증한다. 개발자의 자체 점검을 독립 QA 결과로 대신하지 않는다.
2. 검증 오류가 발생하면 먼저 원인을 분석하고, 재시도는 최대 1회만 수행한다. 최초 실행과 재시도를 구분하여 기록하며 재시도 자체가 의무는 아니다. 동일 사례의 이름을 바꾸거나 작업을 다시 열어 횟수를 초기화하지 않는다.
3. 동일 오류가 반복되거나 검증 환경 문제로 진행할 수 없으면 해당 항목의 재시도를 즉시 중단한다. 명백한 환경 차단은 남은 1회를 소모하려고 다시 실행하지 않는다.
4. 코드 수정이나 환경 변경이 필요하면 QA는 임의로 수정하지 않고 총괄에게 보고한다. 총괄이 조치를 판단하고 담당자, 수정 범위와 공유 Editor 조작권을 정한다.
5. 오류 보고에는 아래 양식의 모든 정보를 포함한다. 원문 로그는 증거 경로와 필요한 오류 부분으로 남기고, 확인된 사실과 추정 원인을 구분한다.
6. 검증을 완료하지 못한 작업은 절대 성공으로 판정하지 않는다. 항목별로 실패(실행했으나 기대 결과 불충족), 차단(환경·의존 문제로 진행 불가), 미검증(아직 수행하지 않음)을 구분한다. 일부 통과를 전체 완료로 표현하지 않는다.
7. 총괄의 명시적인 추가 지시 전에는 차단된 검증을 반복하지 않는다. 시간 경과, 새 턴, 다른 역할의 완료 메시지만으로 재개하지 않는다. 재개 시에도 기존 실패·차단 기록을 보존하고 수정 후 실패·새 영향 항목만 확인한다.
8. 해당 오류와 무관하고 같은 차단 환경에 의존하지 않는 다른 검증은 계속 진행한다. 공용 자원이나 데이터 안전에 영향이 있으면 영향받는 항목만 보류하여 보고한다.

```text
검증 대상 / 변경 파일·상태:
테스트 항목 / 기대 결과:
발생 오류 / 실제 결과 / 로그·증거 경로:
오류 발생 단계:
재시도 결과: 최초 실행 결과, 재시도 0회 또는 1회 결과 (미시도 시 이유)
추정 원인 / 확인 근거:
검증 상태: 실패 / 차단 / 미검증 (항목별 표시)
총괄에게 요청할 조치:
계속 진행할 무관한 항목 / 보류 항목:
```

규칙을 알리거나 기억 여부만 확인하기 위한 담당자 호출, 정기 알림, 자동 재시도는 추가하지 않는다. 운영 문서만 바뀐 작업은 그 영향에 맞는 내용·연결·형식 검사로 확인하며 관련 없는 앱 실행이나 게임 회귀 검증을 추가하지 않는다.

## 작업 기록과 완료 이미지

필요한 작업 기록은 다음 정보로 간결하게 유지합니다. 모든 참여자가 한 공용 파일을 동시에 수정하지 않습니다.

```text
작업명 / 사용자 요청과 승인 근거:
담당자 / 검토자 / 필요한 스킬:
목표 / 완료 조건 / 검증 범위:
수정 소유 파일·범위 / 공유 앱 조작 담당:
선행 작업 / 인터페이스 / 필요한 협의:
상태: 배정 / 진행 / 의존 대기 / 검증 / 완료 / 실패 / 차단 / 미검증
변경 결과 / 검증 근거 / 남은 문제:
인계 대상 / 소유권·조작권 반환:
```

보고 길이는 실제 작업·필수 조율·검증을 줄이는 기준이 아닙니다. 중간 이미지는 사용자 요청·시각적 판단·오류 증거 등 꼭 필요한 때만 기존 대표 이미지 1장을 우선 사용합니다. 새 이미지·화면·UI·디자인·3D 결과를 만든 담당자는 자신의 회의실 완료 보고에 실제 최종 상태의 대표 이미지 1장을 반드시 직접 첨부합니다. 다른 채팅에서만 보여 주기, 경로만 적기, 중간 시안 게시 또는 총괄에게 대신 게시해 달라는 요청은 완료 첨부를 대체하지 않습니다.

총괄은 다음 필요한 배정에서 해당 담당자의 `room_claim(requireFinalImage=true)`와 완료 조건을 지정합니다. 이미 진행 중인 작업에도 재배정 없이 조건을 추가할 수 있으며, 지정 후에는 해제할 수 없습니다. 이 조건의 작업은 담당자 본인의 최종 이미지 첨부 없이는 완료 처리할 수 없고, 담당자가 완료하기 전에 총괄이 성공으로 마무리할 수 없습니다. 중단 복구로 담당자를 바꿔도 조건은 이어집니다. 서버는 파일 첨부 여부를 검사하며 실제 최종 상태인지의 책임은 만든 담당자에게 있습니다.

생성한 이미지의 최종 파일이나 최종 상태를 정확히 보여 주는 기존 이미지를 재사용하고, 필요하면 허용된 범위에서 한 번 캡처합니다. 생성·캡처·파일 접근이 불가능하면 차단 사유를 기록하고 성공 완료로 표시하지 않습니다. 총괄은 통상 통합 과정에서 담당자의 게시물을 확인하며, 이미 올라온 이미지를 중복 첨부하거나 규칙 공지를 위해 담당자를 따로 호출하지 않습니다. 자세한 첨부 형식과 현재 제한은 같은 패키지의 [운영 스킬](../SKILL.md#images-during-work-and-at-completion)을 따릅니다.
